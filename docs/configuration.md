# Configuration

Settings from the environment, the config file and plug-in sources, branding and languages.

## Settings

- `SKOPAX_SECRET_KEY`: signs login sessions and seals every integration secret (tokens and passwords of plug-in instances). Recommended; set it to a long random value. If unset, a key is generated once and kept in the database. Setting it later seals the stored secrets again with the new key on the next start. If the generated key is lost from the database, the sealed secrets cannot be opened: every secret has to be entered again. Once set, keep the same value: after a change from one value to another, Skopax cannot open the integration secrets sealed with the old one, so each has to be entered again in Admin, and everyone has to sign in again.
- `SKOPAX_ADMIN_EMAIL`, `SKOPAX_ADMIN_PASSWORD`: an admin account created from the environment. They apply only while no active admin account exists; once one does, they are ignored (see [Lost setup code](operations.md#lost-setup-code)).
- `SKOPAX_PUBLIC_READ`: default `false`. When `true`, anyone who can reach the page can read the board without signing in. A value saved on the Read without login card in Admin > Features overrides this setting; see [Feature switches](setup.md#feature-switches) for going back to it.
- `SSO_DEFAULT_ROLE`: the role of an SSO user when no resolver, claim or Admin-set role gives one: `viewer` (default) or `operator`. The other sign-in settings are listed under [Headless setup](sign-in.md#headless-setup).
- `SKOPAX_TOKEN`: an optional bootstrap API token; set it to a long random value (it acts as an admin). Prefer tokens created in Admin > Access & sign-in, which carry their own role and can be revoked. Neither kind opens MCP.
- `FORWARDED_ALLOW_IPS`: see [Behind a proxy or ingress](operations.md#behind-a-proxy-or-ingress).
- `PROMETHEUS_URL`: the Prometheus the board reads. It defines the primary Prometheus instance, named `main`. `PROMETHEUS_UI_URL` is the address people open for its graph links (default: the URL), and `PROMETHEUS_NAMESPACES` is the pattern of the namespaces it watches (default `.*`). Without it, and without an instance added in Admin, the Prometheus checks do not run. See [Plug-ins](plugins.md#plug-ins).
- `SKOPAX_BASE_URL`: public URL of this instance. Slack and Teams posts need an absolute URL for their links, and they always use this base when it is set (or the host of `SSO_REDIRECT_URI` when it is not); only with neither set does a post sent from the page link to the address the request came in on. Cookies are marked Secure when it starts with `https://`. Single sign-on needs it: the redirect URI is this base followed by `/authorized`, unless `SSO_REDIRECT_URI` is set.
- `SKOPAX_SELF_REVIEW`: self-review is off by default; set it to `true` and set `SKOPAX_SELF_PROJECT` to turn it on.
- `SKOPAX_WORKSPACE_LABEL`, `SKOPAX_WORKSPACE_LINKS`, `SKOPAX_WORKSPACE_ICON`: the workspace switcher and the picture on its tile (`letter`, `company` or `upload`); see [Other workspaces](setup.md#other-workspaces). Admin > Workspaces edits the list as rows and picks or uploads the icon. The deprecated name `SKOPAX_ENV_LABEL` is also accepted in place of `SKOPAX_WORKSPACE_LABEL`.
- **List editor in Admin.** A setting that holds a list is edited as chips: type an item and press Enter or comma, paste a comma, space or line separated text to split it into chips, press Backspace in the empty box to remove the last chip, or use a chip's cross. An item that does not fit its kind is red with the reason and the row cannot be saved until it is fixed. The stored value is plain text: items joined by a comma and a space, or by a single space for `SSO_SCOPE`. It covers the MCP allowed clients, the self-review recipients, the Jira projects, the Slack push users and question channels (with `all` and `main` as buttons), the certificates not watched, and the SSO scope on the Single sign-on card; the allowed e-mail domains keep their own chips there.
- `SKOPAX_FEATURE_*`: starting values for the feature switches; see [Feature switches](setup.md#feature-switches).
- `SKOPAX_AI_PROVIDER` (`investigate.provider`): `anthropic` (default) or `openai`, the default provider: its default model serves each use whose model is not set. Each use can pick a model of any provider. A use whose chosen model runs on a provider with no working key, or on a compatible connection that is gone or whose key cannot be read, never moves to another provider: the chosen provider is not usable; runs of this use are held, and Admin says so. Another value falls back to `anthropic` with a warning. Admin > Investigator lists it as Default provider; see [The AI provider and its key](setup.md#the-ai-provider-and-its-key).
- `ANTHROPIC_API_KEY` (`anthropic.api-key`): the Anthropic key, used unless one is set in Admin > Investigator.
- `OPENAI_API_KEY` (`openai.api-key`): the OpenAI key, used unless one is set in Admin > Investigator. Each model call uses the key of the provider its use runs on; Test connection on a card sends that card's key.
- `SKOPAX_ALLOW_PRIVATE_AI` (`core.allow-private-ai`): default `false`. While off, an OpenAI-compatible AI connection may not point at a private or loopback address; turn it on to use, for example, a local Ollama. Link-local and cloud metadata addresses are refused either way. Admin > Investigator lists it as Private AI addresses; see [OpenAI-compatible connections](#openai-compatible-connections).
- `SKOPAX_VERTEX_TOKEN_DIR` (`core.vertex-token-dir`): default `/var/run/secrets/tokens`, the usual mount of a projected service-account token. The only directory a Vertex AI federation config may read its token file from; a config that points anywhere else is refused when it is saved, when the client is built and on every credential refresh, so a token file replaced later by a link to another place is refused and the use is held. It is not an Admin setting, so only the deployment can widen it. See [Claude on Vertex AI](#claude-on-vertex-ai).
- `SKOPAX_TIMEZONE`: timezone for day boundaries and display, default `UTC`.
- `SKOPAX_LOG_FORMAT`, `SKOPAX_LOG_COLOR`, `SKOPAX_LOG_LEVEL`: the log format (`text`, the default, `json` or `log4j`), colour (`always`, the default, `auto` or `never`; a non-empty `NO_COLOR` turns it off, whatever Admin or a settings source says) and level (`DEBUG`, `INFO`, the default, `WARNING` or `ERROR`). Admin > Settings lists them as Log format, Log colour and Log level, and a value saved there applies at once; the first lines of a start always follow the variables. See [Logs](operations.md#logs).
- `SKOPAX_DISPLAY_NAME`: the name shown to people on the page, in the chat and in Slack; default `Skopax`. The characters `<`, `>`, `&`, `"`, control characters (including the C1 range) and unpaired surrogates are dropped and the name is cut at 40 characters. The name also names the MCP server, as a lowercase slug of letters, digits and hyphens, so changing it renames the tools in connected clients.
- `SKOPAX_LANGUAGE`: the outbound language, default `en`: the language of what Skopax sends to Slack, Teams, Jira and direct messages. It is `en`, a built-in language, or a language that a serving plug-in's locale pack adds; see [Languages](#languages). Admin > Settings shows it as Outbound language.
- `SKOPAX_ORG_ABOUT`: a few sentences about the company and what Skopax watches: products, main services, who uses them. The investigator reads it in every run (cards, asks, Slack, chat, deploy reports and the self-review) as an About the company block at the start of its instructions, and the topic gate reads it too; an empty value adds no block. At most 2000 characters (it was 300). Admin > Investigator shows it as About your company in a resizable box, and a value saved there applies at once.
- `INVESTIGATE_MODEL_CRITICAL` (`investigate.model-critical`) and `INVESTIGATE_MODEL_HIGH` (`investigate.model-high`): the model of card runs and Investigate clicks on Critical and on High cards, for example a stronger model for Critical cards only. Empty, the default, uses the Card model (`INVESTIGATE_MODEL`). The severity counts when the run starts, so an escalated card gets the new model on its next run, and a run over several cards follows the highest severity among them. Page asks, deploy-report assessments, Slack answers, chat, the topic gate, the self-review and thread summaries keep their own models, and effort stays `INVESTIGATE_EFFORT`. The run records the model used, so spend shows its share. A model that is not known falls back to the Card model; a model whose provider has no working key is held (the chosen provider is not usable; runs of this use are held); Admin > Investigator says so in the Who does what table. Admin lists them next to Card model as Model for Critical cards and Model for High cards.
- `INVESTIGATE_GUARD_MODEL` (`investigate.guard-model`): empty by default, which turns the guard off. The model of the guard, a separate model of any provider that checks questions before the investigator runs and answers before they are posted; see [Guard model](setup.md#guard-model). Admin > Investigator > Who does what lists it as the Guard row.
- `GUARD_CHECK_QUESTIONS` (`guard.check-questions`) and `GUARD_CHECK_ANSWERS` (`guard.check-answers`): default `false`. Turn the question check and the answer check on. Each needs a guard model: without one it has no effect, and Admin refuses to turn it on. Every change, turning a check off included, is listed in Changes.
- `GUARD_MODE` (`guard.mode`): `enforce` (default) or `watch`. With `watch` the guard records what it would have done but never refuses, hides, holds or rewrites anything, and a failed check lets the answer through, so it protects nothing; use it for a few days to see how often the guard would step in. Any other value is read as `enforce`. Every change is listed in Changes.
- `GUARD_ON_HOLD` (`guard.on-hold`): `fix` (default) or `review`. With `fix`, a held answer goes back to the investigator once to be rewritten and is checked again; if it is held again or a check fails, a fixed line is posted instead and the run's card writes and proposals are dropped. With `review`, held answers wait for an admin to release or discard them, as in 0.6.4. Any other value is read as `fix`.
- `CHAT_EFFORT` (`chat.effort`): the thinking effort of the chat model (`low`, `medium`, `high`, `xhigh` or `max`). The default is `medium`, the same as the Slack effort (`investigate.slack-effort`); the two are independent. An empty `CHAT_EFFORT` counts as not set. Admin > Investigator lists it next to Chat model.
- `CHAT_MAX_TOOL_CALLS` (`chat.max-tool-calls`): the most tool calls one chat answer may use, 3 to 30. `0`, the default, follows the Slack cap (`investigate.slack-max-tool-calls`), which is what chat used before. Slack asks keep their own cap.
- `INVESTIGATE_WEB_DOMAINS` (`investigate.web-domains`): the sites the investigator may search and read on the web. The built-in documentation sites are always included, and your own websites (`SKOPAX_OWN_SITES`, below) join them. Hosts you list are added to that list; write `-host` (for example `-blog.google`) to leave a built-in one out; `any` lifts the limit and `off` turns web search and reading off. Admin > Investigator shows the built-in list under the setting. Upgrade note: an install that listed its own sites used to get only those, and now also gets the built-in ones.
- `SKOPAX_OWN_SITES` (`core.own-sites`): Your websites, the sites of your company the investigator may read and search, such as `example.com`, separated by commas or spaces. Host names only, without `https://`, a path or a port: a pasted address in the environment or the config file is left out with a warning in the log, and Admin refuses it with a message. A host covers its subdomains. These sites lead the built-in list under Web sites (`INVESTIGATE_WEB_DOMAINS`), and writing `-example.com` there leaves one out. Empty, the default, uses the sites (the `url` host and the `hosts` field, login hosts left out) of the enabled Website integrations, and Admin > Investigator says under the row which source is in use. A value saved in Admin overrides this one and applies at once. Upgrade note: the e-mail domains of sign-in (`SKOPAX_EMAIL_DOMAINS` and the organisation pack) no longer count as your websites; set Your websites or rely on the Website integration. Sign-in itself is not affected.
- `SKOPAX_LINK_HOSTS` (`core.link-hosts`): comma-separated hosts that Skopax may link to in what the investigator posts, next to its own address and the addresses of your plug-in instances. An entry such as `example.com` also allows every subdomain, `docs.example.com` included. Write `=example.com` to allow that host only: `sub.example.com`, `example.com.evil.test` and `evilexample.com` are then refused. Another source of the same host, such as a plain entry or a plug-in's address, keeps its wider reach.
- `JIRA_BACKLINK` (`jira.backlink`): `link` (default), `comment` or `off`. What Skopax adds to a Jira issue when a card gets it as its ticket: a web link to the card, one short comment with the card link, or nothing. Admin > Settings lists it under Jira tasks as Back-link on the issue, and a value saved there applies at once. Another value falls back to `link` with a warning; see [Jira](plugins.md#jira).
- `SKOPAX_PROBE`: default `true`. Switches the reachability probe; see [Probe](operations.md#probe). Admin > Features lists it under Other switches as Reachability probe, and a value saved there overrides this one and applies at once.
- `SKOPAX_UPDATE_CHECK`: default `true`. Switches the daily check for a newer release; see [Version check](operations.md#version-check). Admin > Features lists it as Check for new versions, and a value saved there overrides this one and applies at once.
- `SKOPAX_FEATURE_LANGFUSE_TRACING` (`core.langfuse-tracing`): default `false`. Sends every AI call of Skopax to a Langfuse project as a trace; see [Langfuse tracing](plugins.md#langfuse-tracing). Admin > Features lists it as Langfuse tracing, and a value saved there overrides this one and applies at once. While it is off, or no instance is picked, nothing is traced and no request is made.
- `LANGFUSE_TRACE_INSTANCE` (`langfuse.trace-instance`): the name of the Langfuse instance (Connect > Integrations) that the traces go to; empty, the default, sends nothing, and the Langfuse tracing switch in Admin > Features then says it needs one. Admin > Investigator > Langfuse tracing lists it as Langfuse instance, with the configured Langfuse instances to pick from.
- `LANGFUSE_TRACE_CONTENT` (`langfuse.trace-content`): `metadata`, the default, sends names, models, tokens, cost, timing, status, card keys and run ids only. `full` also sends the prompts, questions, answers and tool output, through the same redaction as plug-in output and cut to 4000 characters each. Warning: full content can hold customer data, and it then sits in the Langfuse project for everyone who can read it. Any other value reads as `metadata`, with a log line.
- `LANGFUSE_TRACE_SAMPLE` (`langfuse.trace-sample`): the share of traces sent, from 0 to 100, default `100`. It is decided once per trace; a failed run or call is always sent.
- `SKOPAX_TAG_REPORT_AT` (`tags.report-at`): default `10:00`. The time of day, as HH:MM in the install time zone (`SKOPAX_TIMEZONE`), of the daily Slack tag report, from `00:00` to `23:55`; empty turns it off. It posts Monday to Friday only, and only in the two hours from that time; a start after the window skips the day. Admin > Settings lists it under Card tags as Daily report at, and a value saved there overrides this one and applies at once; see [Card tags and responsibles](setup.md#card-tags-and-responsibles).
- `SKOPAX_TAGS_MAIL` (`tags.mail`): default `true`. Mails each tag responsible their part of the daily tag report, of the daily warnings digest and of the plug-in digests that name their tags, through the Mail server and apart from Slack; see [Card tags and responsibles](setup.md#card-tags-and-responsibles). Admin > Settings lists it under Card tags as Mail responsibles their part.
- `SKOPAX_CERT_RULES`: the thresholds of the certificate cards as JSON, default `{"warn_days": 21, "crit_days": 7}`. Admin > Settings lists them under Monitor rules as Certificates. Certificate cards are made for HTTPS probe targets whose certificate verified, and an expired certificate still gets its critical card. Probe target URLs and errors are shown to admins only.
- `SKOPAX_CERT_SKIP`: hosts whose certificate raises no card, separated by commas. `shop.example.com` also covers its subdomains, `*.example.com` covers only the subdomains. Admin > Settings lists it under Monitor rules as Certificates not watched. A skipped host still counts as checked, so a card it already has closes on the next probe.
- `SKOPAX_PROBE_EXTRA`: extra addresses for the reachability probe, one `name=url` per line, at most 20, default empty. Names are 1 to 40 letters, digits, spaces, dots, dashes or underscores and unique; addresses are http or https without a user name or password. Only reachability is checked and no credentials are sent. Admin > Settings lists it under Monitor rules as Extra probe targets. The probe also checks Slack, the AI provider in use and the Google hosts of serving Google plug-ins by itself; see [Probe](operations.md#probe).
- `SKOPAX_AUTO_RESOLVE_HOURS_CRIT`, `SKOPAX_AUTO_RESOLVE_HOURS_HIGH` and `SKOPAX_AUTO_RESOLVE_HOURS_WARN` (`core.auto-resolve-hours-crit`, `core.auto-resolve-hours-high`, `core.auto-resolve-hours-warn`): default `6` each, from 0 to 720, where 0 turns the rule off for that severity. Info cards have no window here: a cleared info card leaves the page 24 hours after it cleared and is not auto-resolved. A card that stopped firing and that nobody acted on (nobody took it, linked a ticket, muted it or sent the investigator) is closed as auto-resolved after the hours of its current severity; a card that fires again inside the window is not closed. A card assigned to someone (by hand or by auto-assign) but not taken waits three times the window of its severity, counted the same way, before it is auto-resolved; a plug-in window still skips an assigned card. Every wait counts from the latest of when the card cleared, when it was last assigned and when it was reopened, so a new assignee or a reopened card gets the full window. The assignee's Notifications page names the reason under the auto-resolved card, such as "Cleared 14 Oct 07:59, nobody acted in 18 hours". Its note and the Slack thread line say "Did not recur for 6 hours", or whole days ("3 days") when the hours divide by 24, using that severity's window. An event card without a ticket waits 6 hours longer than its window. The high window without a value of its own follows the warning window, so cards that moved from warning to high in 0.5.8 keep the window they had. Admin > Cards shows the three as one row, Auto-resolve cleared cards after (hours), with an input each for Critical, High and Warning. Plug-ins can give some card kinds a window of their own, counted from when the card first appeared: VWO A/B result cards and Google Ads disapproved-ads cards close after 24 hours by default (`vwo.auto-resolve-hours`, `google-ads.auto-resolve-hours`; 0 uses the general rule). A card of such a kind follows its own window and not these. While Business days only (below) is on, these hours and the plug-in windows count only Monday to Friday.
- `SKOPAX_AUTO_RESOLVE_HOURS` (`core.auto-resolve-hours`): deprecated and hidden in Admin, use the severity settings above. It is still read, from the environment, the config file, a settings source or a value stored in Admin: the critical and warning windows that have no setting of their own use it, and the high window follows the warning window. A severity setting that is set always wins over it. In Admin, a window that takes its value from an old value stored there shows an old setting tag; Reset or saving either window clears the old stored value and keeps the other window as it is. `SKOPAX_AUTO_RESOLVE_DAYS` (`core.auto-resolve-days`) still feeds this old key.
- `SKOPAX_INFO_AUTO_CLOSE_DAYS` (`core.info-auto-close-days`): deprecated, hidden in Admin and ignored. Info findings are not cards: they show on the Information page while they fire and for a day after they end, and are never closed. The value is still read for compatibility, and a log line says it is ignored when it is set.
- `SKOPAX_BUSINESS_DAYS` (`core.business-days`): default `true`. While on, the auto-resolve windows (critical, high, warning, the deprecated `core.auto-resolve-hours` and the plug-in windows such as `vwo.auto-resolve-hours`) count only time from Monday 00:00 to Friday 24:00 in the install time zone (`SKOPAX_TIMEZONE`, default `UTC`); weekend time does not count. A warning card that stopped firing on Friday at 22:00 with the default window of 6 hours closes on Monday at 04:00. The note, the activity line and the Slack thread line then say business hours or business days, such as "Did not recur for 6 business hours". `false` counts every hour, weekends included. Posting cards to Slack or Teams is not changed: alerts still post on any day. Admin > Cards lists it as Business days only, and a value saved there applies on the next pass.
- `SKOPAX_FEATURE_SETTLE` (`core.settle`): default `true`. Switches the settle review of waiting cards; see [Follow-up checks and settle reviews](plugins.md#follow-up-checks-and-settle-reviews). Admin > Features lists it as Settle waiting cards, and a value saved there overrides this one and applies at once. It needs the investigator in live mode; while it is off, follow-up checks of a done-condition still run.
- `INVESTIGATE_FOLLOW_UP_HOURS` (`investigate.follow-up-hours`): default `6`, from 1 to 72. How long a waiting card waits between two follow-up checks or settle reviews; the first follow-up check of a done-condition runs an hour after the investigator wrote it.
- `INVESTIGATE_FOLLOW_UP_DAYS` (`investigate.follow-up-days`): default `7`, from 1 to 30. After this many days of follow-up checks that did not confirm the fix, the check gives up: the card shows gave up and is left to people. Until then, a stopped card with a pending done-condition is not auto-resolved by the auto-resolve windows; afterwards they apply again from that moment.
- `INVESTIGATE_FOLLOW_UP_CLOSE_HOURS` (`investigate.follow-up-close-hours`): default `6`, from 1 to 48. How long after a check that found a waiting card fixed or over the card closes, unless it fires again, a person acts on it or someone presses Keep open. While Business days only is on, these hours count only Monday to Friday, like the auto-resolve windows.
- `INVESTIGATE_SETTLE_MAX_PER_DAY` (`investigate.settle-max-per-day`): default `20`, from 0 to 200; 0 turns follow-up checks and settle reviews off. The most follow-up checks and settle reviews per day, all cards together, counted from local midnight. They also count against the daily limit (`investigate.daily-usd`). When either limit is reached the rest wait, and the log says so once; cards never checked go first, then those checked longest ago.
- `SLACK_POST_SEV` (`slack.post-sev`): default `high` (it was `warn` before 0.5.8; a value set in the environment, the config file or Admin is kept). A card of this severity or higher is posted to the main Slack channel with its numbers when it is pushed (new, escalated or reopened; info findings are never posted); the investigator's findings follow in its thread. `crit`, `high`, `warn` or `off`; the retired `info` reads as `warn`, with one log line. Admin > Settings > Slack lists it as Post immediately from (Critical, High, Warning, Off), and a value saved there applies at once. Slack auto-send must be on. When more than 3 cards are due in one pass, none is posted at once. See [Slack](plugins.md#slack).
- `ROUTES_WAIT_MINUTES` (`routes.wait-minutes`): default `30`, from 5 to 240. How long a Teams or Email route that is not for a business team waits for the investigator to finish a card below Post immediately from; after that it sends the plain card; with a finished investigation it sends at once, with the finding. Admin > Settings lists it under Slack next to the route settings. See [Microsoft Teams](plugins.md#microsoft-teams).
- `SLACK_WARN_DIGEST_AT` (`slack.warn-digest-at`): default `09:30`. The time of day, as HH:MM in the install time zone (`SKOPAX_TIMEZONE`), of the daily Slack post that lists the Warning cards nobody has picked up, from `00:00` to `23:55`; empty turns it off. Since Warning cards are not posted at once by default, this is where the channel sees them. It posts Monday to Friday only, and only in the two hours from that time; a start after the window skips the day, and it never posts late. Admin > Settings lists it under Slack as Warnings digest at, and a value saved there overrides this one and applies at once; the switch is Daily warnings digest in Admin > Features (`SKOPAX_FEATURE_WARN_DIGEST`). See [Slack](plugins.md#slack).
- `SLACK_THREAD_SUMMARY` (`slack.thread-summary`): default `true`. Writes a short summary of a card's Slack thread onto the card after Skopax answers there and when the thread has been quiet for 30 minutes, and pauses while the investigator is off, stopped or capped; Admin > Settings > Slack lists it under Questions as Summarise Slack threads onto cards. See [Slack](plugins.md#slack).
- `SKOPAX_ALERTS_WARN` (`alerts.warn`): empty by default. Alert names, separated by commas, whose `warning` label stays Warning instead of High, such as `*Forecast*, CephPoolGrowthForecast`; `*`, `?` and `[...]` match, case counts, at most 100 names, and an entry that is not an alert name is skipped with one log line. Admin > Settings > Cards lists it as Alerts kept at Warning. See [Severities](plugins.md#severities).
- **Severities.** A card is Critical (`crit`), High (`high`), Warning (`warn`) or Info (`info`), in that order. High is for problems users feel now, such as 5xx and error-log spikes, a broken page or ad link, traffic down by more than half and a failed deploy; Warning is for forecasts, slow growth, cost and housekeeping. A card whose value doubles since it was last pushed moves one level up, from Warning to High and from High to Critical, and stays there while it lives; a severity set by hand is not moved. A WARN log pattern is High when it is new with at least 100 lines in the hour or at least 10 times its day or its week baseline with at least 50 lines, and a latency card is High at 3 times its baseline over at least 500 requests; these thresholds are fixed constants, not settings. See [Severities](plugins.md#severities).
- **Upgrading to 0.7.1.** Nothing to set and no migration; old and new pods can run side by side during a rolling update. Admin > Integrations gains a Recently opened row, kept in each browser's local storage only.
- **Upgrading to 0.7.0.** Nothing to set and no migration; old and new pods can run side by side during a rolling update. Search by meaning is off by default and stays off until `SKOPAX_EMBED_URL` points at an embedding service and the feature is switched on; see [Search by meaning](operations.md#search-by-meaning). Card history now also keeps the card description, so new occurrences carry it. The Grafana plug-in gains the Tempo trace tools; its token needs `datasources:query` on the Tempo datasources to use them. Plug-ins built for 0.6 declare `core` below 0.7 and need their range raised to load.
- **Upgrading to 0.6.6.** Nothing to set and no migration; old and new pods can run side by side during a rolling update. Guard mode defaults to `enforce`, so the guard keeps checking and enforcing exactly as in 0.6.5. On hold defaults to `fix` on new and existing installs alike: an answer the guard holds is now rewritten once and checked again, and dropped with a fixed line if it is held again, instead of waiting for an admin. Set On hold to Send to an admin (`guard.on-hold` = `review`) to keep the 0.6.4 held-answer queue. Answers with accuracy problems only are now posted with a note for admins instead of held. A run whose final reply had text before a web search or advisor call now posts only the text after it.
- **Upgrading to 0.6.5.** Nothing to change: no migration and nothing to set, and old and new pods can run side by side during a rolling update. A guard or topic gate on a Claude Opus or Sonnet model now works.
- **Upgrading to 0.6.4.** The guard is off by default: no guard model is set and both checks are off, so nothing changes, there is no migration and nothing to set, and old and new pods can run side by side during a rolling update. Once a guard model and a check are set, see [Guard model](setup.md#guard-model). The Available in questions choices and the MCP tools server's chat-role choices have new labels (Card runs + everyone's questions, Card runs + operator and admin questions, Card runs + admin questions, Card runs only); only the labels change, stored values stay as they are.
- **Upgrading to 0.6.3.** The advisor changes nothing until it is set: the Advisor model of each investigator use is None by default, there is no migration and nothing to set, and old and new pods can run side by side during a rolling update. See [Advisor model](setup.md#advisor-model). Chat effort no longer has a Same as Slack choice: it is always one of Low, Medium, High, Extra high or Max, `medium` by default. ## OpenAI-compatible connections

Besides Anthropic and OpenAI, Skopax can call any service that speaks the OpenAI Chat Completions API: DeepSeek, Groq, Together, Mistral, OpenRouter, a local Ollama or vLLM, and others. Each one is a named connection, kept in the database like the AI keys:

- Name: 1 to 20 characters, lower-case letters, digits and dashes (the same rule as integration instance names), such as `deepseek`.
- Base URL: the API root, such as `https://api.deepseek.com/v1`. It must start with `http://` or `https://`, and must not carry a user name, password, query or fragment; the key goes in the key field.
- Key: optional (a local Ollama needs none), 1 to 400 characters with no spaces. It is sealed with the secret key, never shown again, and never written to logs or error texts. Saving without a key keeps the stored one.
- Models: up to 50, each an id as the service names it, with an optional input and output price in USD per million tokens (both or neither). A model without a price is charged at the highest known rate, and its ledger rows say which model it was priced as (`pricedAs`).
- Uses tools (on by default) and Reads images (off by default). With images off, an attached image is left out and the model is told "images not sent: this model does not read images".

A model of a connection is named `<connection>/<model>`, such as `deepseek/deepseek-chat`; the part after the first `/` is sent to the service as it is, so OpenRouter ids that hold a `/` work. A compatible model gets no web search or page reads, no thinking settings, no server-side fallbacks and no prompt caching marks.

Before a connection is saved, and again on every connection the server opens, its host is resolved and each address is checked, so a name that later resolves somewhere else is still refused. Private and loopback addresses are refused unless `core.allow-private-ai` is on; link-local and cloud metadata addresses are always refused. Connections made this way do not use the `HTTPS_PROXY` settings of the environment. They send no `OpenAI-Organization` or `OpenAI-Project` header and follow no redirects, and a saved key is never sent to a base URL on another host until it is entered again.

Test connection sends two requests: a one-line question, then one forced call of a dummy `echo` tool. The result reads "Answers, uses tools", "Answers, but did not call the tool: not fit for investigations", or what went wrong. Cheap models often miss steps in long investigations, so test a model before it runs card investigations.

The Admin API (admin only, same-origin like the other Admin calls):

- `GET /api/admin/ai-connections`: every connection, with `key.set` in place of the key and the last test result (`lastTest`).
- `PUT /api/admin/ai-connections/{name}`: create or replace one (`baseUrl`, `key`, `models`, `tools`, `images`).
- `DELETE /api/admin/ai-connections/{name}`: remove one.
- `POST /api/admin/ai-connections/{name}/test`: test the saved connection, or values typed but not saved yet.

## Claude on Vertex AI

Skopax can run Claude through your own Google Cloud project on Vertex AI (Claude Models on Google Cloud, Google managed), so prompts and answers are processed at the endpoint you pick, under your Google Cloud contract and billing. Each one is a named connection, kept in the database like the AI keys:

- Name: the same rule as other connections (1 to 20 characters, lower-case letters, digits and dashes), and no other AI connection may have it. A model is named `<connection>/<model>`, such as `vertex-eu/claude-opus-5-5`.
- Project: the Google Cloud project id (6 to 30 characters).
- Region: `global`, the multi-region `us` or `eu`, or a Google Cloud region such as `europe-west4`. The endpoint is fixed by the region: `aiplatform.googleapis.com` for `global`, `aiplatform.us.rep.googleapis.com` and `aiplatform.eu.rep.googleapis.com` for `us` and `eu`, `<region>-aiplatform.googleapis.com` for a region. Model calls go to no other host, follow no redirects and do not use the `HTTPS_PROXY` settings of the environment. Current Claude models run only on `global`, `us` and `eu`; a single region serves Claude Sonnet 4.6 and earlier only. `eu` is the choice that keeps processing in the European Union; `global` gives no residency guarantee. Which region serves which model is Google's table; Test connection tells you when a model is not served where you picked.
- Credentials, one of three modes:
  - `key`: the JSON key file of a service account. It is sealed with the secret key, never shown again and never written to logs, errors, traces or Changes. Saving without it keeps the stored one, but changing the project or the region asks for it again, so a saved key is never used for another project or region. Only the `service_account` type with Google's own token endpoint is accepted.
  - `federation`: a workload identity federation config (`external_account`), which holds no secret: Google trusts the OIDC service-account tokens of your Kubernetes cluster. It must read the token from a file (`credential_source.file`) under `SKOPAX_VERTEX_TOKEN_DIR`; URL and executable sources, other endpoints than Google's token service and any other file path are refused.
  - `pod`: the Google identity of the pod (Application Default Credentials, such as GKE workload identity). Nothing is stored.
- Models: up to 20, each with a Skopax name, the Vertex model id (never guessed: older models carry `@<date>`) and optional input and output prices in USD per million tokens (both or neither). A model without prices starts from the Anthropic list price when the id is known; check your Google Cloud price sheet, since regional and multi-region endpoints cost more than `global`. Cache reads are charged at 0.1, 5-minute cache writes at 1.25 and 1-hour cache writes at 2 times the input price, and a web search at $0.01.

The role the identity needs is Agent Platform User (`roles/aiplatform.user`, permission `aiplatform.endpoints.predict`) on the project, and Claude must be enabled for the project in Model Garden. Skopax calls no other Google API with these credentials; the credentials library only contacts Google's token endpoints to sign in (and the metadata server in `pod` mode).

A run on Vertex gets tools, images, PDFs, adaptive thinking and effort, prompt caching (5-minute and 1-hour) and basic web search (`web_search_20250305`). It never sends page reads (web fetch), server-side `fallbacks`, batches, files, MCP connector or `inference_geo`. A use whose Vertex connection is gone, has no readable key or has a token path outside the allowed directory is held, never sent to another provider. A use that still points at a model removed from the connection is not moved to the Card model either: the model counts as unknown, its row in Admin > Investigator shows the problem and a notice says so until you pick another model.

Test connection sends a one-line question to every listed model and one forced call of a dummy `echo` tool, all to the endpoint of the configured region. It says in plain words when the model is not enabled in that region, when the project or role is missing, when the quota is used up and when Google rejects the credentials.

The Admin API (admin only, same-origin like the other Admin calls):

- `GET /api/admin/ai-vertex`: `items` (every connection) and `regions` (the allowed regions).
- `GET /api/admin/ai-vertex/{name}`: one connection as `{name, project, region, credentials: {mode, set}, models: [{id, vertexId, input, output}], lastTest, company}`; there is no key in it.
- `PUT /api/admin/ai-vertex/{name}`: create or replace one with `{project, region, credentials: {mode, key | config}, models}`. `key` (the key file as text or an object) belongs to mode `key` and `config` (the federation config as text or an object) to mode `federation`; mode `pod` takes neither.
- `DELETE /api/admin/ai-vertex/{name}`: remove one.
- `POST /api/admin/ai-vertex/{name}/test`: test the saved connection, or values typed but not saved yet. It answers `{ok, tools, summary, models: [{id, ok, summary}], ms}`; a test of the saved connection is also kept as `lastTest`.

## Where AI data goes

Every model call sends the text the investigator works with (card details, tool results such as logs and metrics, the question, attached images where the model reads them) to the company that runs the model, after Skopax masks the secrets it recognises:

- Anthropic models (`claude-*`) go to Anthropic.
- OpenAI models (`gpt-*`) go to OpenAI.
- A model of an OpenAI-compatible connection goes to the host of its base URL, such as `api.deepseek.com`, or stays on your network for a local Ollama.
- A model of a Vertex AI connection (`<connection>/<model>`) goes to Google Cloud Vertex AI, in the location of the connection and under your own Google Cloud project: `eu` and `us` keep processing in that multi-region, a single region keeps it there, and `global` gives no residency guarantee; see [Run Claude on Vertex AI in your own Google Cloud](setup.md#run-claude-on-vertex-ai-in-your-own-google-cloud).

Check the data terms of each company before you choose its models for a use. Langfuse tracing, when it is on, sends its own copy to the Langfuse host; see `langfuse.trace-content`.

## Search by meaning

Search by meaning finds earlier runs, cards, deploys, notes and pages by what they say, not by the words they use. It needs an embedding service that speaks the OpenAI embeddings API (`POST /v1/embeddings`), and it stays off until the deployment names one. Only the masked text of an item is sent to that service, and the vectors are kept in the database; the text itself is not.

- `SKOPAX_FEATURE_SEMANTIC_SEARCH` (`core.semantic-search`): default `false`. The switch. It cannot be turned on while `SKOPAX_EMBED_URL` is empty. Admin > Features lists it as Search by meaning, and a value saved there overrides this one and applies at once. Off keeps the word search.
- `SKOPAX_EMBED_URL` (`embed.url`): empty by default. The address of the embedding service, such as `http://skopax-embed:8080`, without a path, query, user name or password; at most 500 characters. Deployment only: it is not an Admin setting.
- `SKOPAX_EMBED_API_KEY` (`embed.api-key`): empty by default. The key sent as a bearer token to the service, if it needs one; plain ASCII without spaces. Deployment only: it is not an Admin setting and is never shown.
- `SKOPAX_EMBED_ALLOW_PUBLIC` (`embed.allow-public`): default `false`. While off, the service must sit on a private or loopback address; turn it on to use a service on a public address. Link-local and cloud metadata addresses are refused either way, and every address is checked again on each connection. Deployment only: it is not an Admin setting.
- `SKOPAX_EMBED_MODEL` (`embed.model`): default `intfloat/multilingual-e5-small`. The model name sent to the service; an answer from another model is refused. Changing it rebuilds the index.
- `SKOPAX_EMBED_QUERY_PREFIX` (`embed.query-prefix`) and `SKOPAX_EMBED_PASSAGE_PREFIX` (`embed.passage-prefix`): empty by default, which uses the model default: `query: ` and `passage: ` for an e5 model and nothing for others. Changing the passage prefix rebuilds the index.
- `SKOPAX_EMBED_TIMEOUT_SECONDS` (`embed.timeout-seconds`): default `3`, from 1 to 60. How long a search question waits for the service.
- `SKOPAX_EMBED_BATCH_TIMEOUT_SECONDS` (`embed.batch-timeout-seconds`): default `60`, from 5 to 300. How long indexing waits for the service for one batch.
- `SKOPAX_EMBED_BATCH` (`embed.batch`): default `8`, from 1 to 32. Texts sent in one call.
- `SKOPAX_EMBED_BACKFILL_PER_PASS` (`embed.backfill-per-pass`): default `200`, from 0 to 5000. The most older items added in one pass; 0 pauses the backfill.
- `SKOPAX_EMBED_DOCS_PER_PASS` (`embed.docs-per-pass`): default `200`, from 0 to 2000. The most documentation pages added in one pass; 0 pauses indexing of pages.
- `SKOPAX_EMBED_MAX_VECTORS` (`embed.max-vectors`): default `300000`, from 1000 to 2000000. The most vectors one pod keeps in memory. Above it the oldest items by their own date are left out, kind by kind.
- `SKOPAX_EMBED_SOURCES` (`embed.sources`): default `runs, cards, changes, knowledge, docs, logs`. What is indexed, separated by commas; a name that is not a source is skipped with a warning. Documentation pages also need the index switch of their integration.
- `INVESTIGATE_SIMILAR_IN_BRIEF` (`investigate.similar-in-brief`): default `true`. Adds a short list of similar earlier incidents to the brief of a card investigation while Search by meaning is on and answering.

Apart from the three marked deployment only, every setting above is also listed in Admin > Investigator and a value saved there applies at once. Until the service has answered once, the status of the service is unknown; after three failed calls in a row it is marked down for 30 seconds, then for longer (up to 10 minutes) while it keeps failing, and word search is used meanwhile.

## Settings sources

Settings and instances come from these sources, in this order:

1. the environment (for example `PROMETHEUS_URL`);
2. the file named by `SKOPAX_CONFIG_FILE`, default `/etc/skopax/skopax.yaml`, read again every minute;
3. sources supplied by plug-ins;
4. Admin.

For a setting, a later source overrides an earlier one. The file may hold only `settings` and `plugins`, and `${NAME}` or `${NAME:default}` in a value is filled from the environment (plain `${NAME}` stops the start if the variable is unset):

    settings:
      core.timezone: ${TZ_NAME:UTC}
    plugins:
      prometheus:
        instances:
          - name: east
            url: http://prometheus-east.example.com:9090

If two sources define an instance with the same name, the first one wins.

A bad value in the environment or the file stops the start and names the field. A bad instance from a plug-in source is parked with a reason shown in Connect > Integrations, and the rest keeps running. If a source fails later, the last good values stay in use. Instances from a source are shown in Admin but edited at their source.

### Spring Cloud Config

The Spring Cloud Config plug-in is a settings source of the third kind: it reads a Spring Cloud Config server and turns chosen keys into Skopax settings and instance fields. It has no form in Admin; it is set by environment variables, and without `SPRING_CONFIG_URL` it supplies no source at all (a settings source hook that returns nothing is skipped). A mapped key or template key the server does not have is logged once per process (again if it comes back and goes again, or when the source setup changes) and listed in Admin notices as "Not in the config server answer", up to 50 keys.

- `SPRING_CONFIG_URL` (the server address, `http` or `https`, with no credentials or query in it), `SPRING_CONFIG_APP` (the application name), `SPRING_CONFIG_PROFILE` (default `default`; a comma list is allowed) and `SPRING_CONFIG_LABEL` (the branch or tag; empty leaves it to the server; a `/` in it is sent as `(_)`). Skopax reads `<url>/<app>/<profile>/<label>`.
- `SPRING_CONFIG_USER` and `SPRING_CONFIG_PASSWORD`: a basic sign-in, both or neither.
- `SPRING_CONFIG_MAP` (required unless `SPRING_CONFIG_TEMPLATES` is set): the map from config keys to Skopax, a comma list of `<config key>=<target>`. A target is a setting id, such as `investigate.max-cards`, or an instance field written `<plug-in id>/<instance name>/<field>`, such as `jira/main/url`; the fields given for one instance name make one instance. One config key can fill several targets: list them with `|` (the documented form), such as `google.api-key=maps/main/key|places/main/key`; repeating the key (`k=a,k=b`) means the same. Every target gets the same value. The targets of one key must be all secret fields or none: a key that would fill a secret field and a plain field or a setting is refused, and the log names the key and its targets, never a value, so a secret is never shown in one place while it is sealed in another. When core does not tell the source the field kinds (see [Hook time limits](extending.md#hook-time-limits)), this cannot be checked: the key still fills its targets, and one log warning names the keys that were not checked. A target can be filled from one entry only (in the map or in `SPRING_CONFIG_TEMPLATES`), a target may not be an instance's `plugin` or `name`, and the old connection keys (`jira.url`, `gitlab.token` and the others core does not read as settings) are refused; any of these stops the start, and the log names the entry. Keys of the server that the map does not name are ignored.
- `SPRING_CONFIG_TEMPLATES` (optional): secret fields built from several config keys, one `<plug-in id>/<instance name>/<field>=<template>` per line. The target must be a secret field of a loaded plug-in (such as `website/shop/scan-headers`); a setting id or a field that is not secret is refused, because a template often holds a secret and only a secret field is sealed and never shown. Lines keep commas, semicolons and `=` in the template, which is why templates have their own variable instead of the comma list of the map; blank lines are skipped and spaces around the target and the template are dropped. A placeholder is `${<config key>}` and nothing else: no default (`${a:b}`), no nesting, no environment lookup and no other expansion; a `$` or `}` outside a placeholder is kept as written. Each placeholder takes the raw value of the key in the answer: a `${...}` inside that value is kept as written and never filled, from the config or the environment. A template with no placeholder, a malformed placeholder, a target that is not a secret field or a target that is already filled stops the start, and the log names the line number and the target, never the template text (a line that does not start with a target is named by its number only). A key the server does not have leaves the whole field unset with one log warning that names the target and the key, never a value; so does a result over 65,536 characters. Only the map or the templates are required, not both. Before removing a plug-in from `SKOPAX_PLUGINS`, or when one fails to load, remove its template lines too: its fields are then not known to be secret, so the template is refused and a main does not start. Example, for a header field of a website instance:

  ```
  SPRING_CONFIG_TEMPLATES=website/shop/scan-headers=X-Automation-Secret: ${pagescan.automation-secret}; X-Automation-Id: ${pagescan.automation-id}
  ```

  The result is held like any value from this source: in Admin the field shows as set by Spring Cloud Config, and since the target is always a secret field, the result is sealed and never shown or logged.
- **Values:** the answer's `propertySources` are read in order and the first source that has a key wins. In a mapped value, `${key}` and `${key:default}` are filled from the config (all sources), then from the environment (the name as written, then in upper case with every other character as `_`), then from the default. The environment lookup reads the whole environment of the Skopax process, so a placeholder naming a secret variable would copy that secret into the mapped setting; keep the config server as trusted as the environment. A null value in the config counts as not there. A placeholder that cannot be filled, one that loops (`${a}` to `${b}` to `${a}`) or an expansion that grows too large leaves that one value out with one log warning that names the config key and the placeholder, never a value. A mapped key the server does not have is left out with a warning too.
- **Time and failure:** one request, with a limit of 8 seconds in all, under the 10 seconds a source hook may take. The answer is kept and read again every 15 minutes; after a failed read the next try waits 5 minutes, and the last good copy stays in use. A main that cannot read the server at start does not start, and the error names the cause (for example `Unauthorized`, `TimedOut`, `EmptyAnswer`); an agent starts on its environment alone and tries again. An answer with no property source counts as a failure, so a mistyped application name does not wipe the settings it gave before.
- Passwords and secret values are never logged.

### Vault

The Vault plug-in is a settings source of the third kind too: it reads settings and instances, secrets included, from HashiCorp Vault or OpenBao (KV version 2). It is set by environment variables only (`VAULT_ADDR`, `VAULT_AUTH` and the others), only reads from Vault, and without `VAULT_ADDR` it supplies no source at all. It is read again every minute, as the config file is, and keeps its last good data when Vault cannot be read. See [Vault](plugins.md#vault) for the variables, the layout and the Kubernetes auth steps.

## Languages

Skopax is written in English and ships built-in language packs for `tr`, `de`, `es` and `fr` (`de`, `es` and `fr` are a preview). They are always on, with no switch. A text a pack does not translate yet shows, or is sent, in English. Plug-ins can add more languages, or reword a built-in one, with their own locale packs (see [Locale packs](extending.md#locale-packs)); a plug-in's text wins over the built-in text for the same language. With Language on Auto, the default, a browser that prefers one of these languages shows the page and the chat in it; English stays one click away in Settings > Appearance. Channel posts, tickets and the card language stay English until an admin picks another outbound or card language. A reply to one person who asked in Slack, such as an off-topic answer or a limit notice, follows that person's language when a built-in pack covers it, so such replies can come in any built-in language with no setting changed. Each place picks its language in its own way:

- **What Skopax sends.** Slack and Teams posts, Jira tickets and direct messages use the outbound language: Outbound language in Admin > Settings, or `SKOPAX_LANGUAGE`. It offers `en`, the built-in languages and each language that a serving plug-in's pack adds, and a regional tag such as `pt-BR` must match a pack's tag. A saved language whose pack has gone stays shown with a hint, and English is sent until a pack adds it again. A text that the pack lacks is sent in English.
- **Replies that follow the asker.** The reply to a Slack question that is off-topic, or over the small-talk or ask limit, is in the language the topic gate reads from the question when a pack has it, including a regional pack for the plain language (`pt` reaches `pt-BR`); otherwise it is in English. A built-in pack counts like a plug-in's pack here. A reply sent without a gate verdict, and every channel post, is in the outbound language that the admin picked.
- **The investigator.** It writes cards, Slack posts and deploy reports in the Card language (Admin > Investigator, or `INVESTIGATE_LANGUAGE`), which offers `en` and each language whose pack has a writing note. It answers a question in the language of the question.
- **The page and the API stay English.** Page packs translate the page in the browser, opened cards included. Settings > Appearance > Language lists Auto, English and one entry for each page pack that is loaded, built-in or from a plug-in, each under its own name (Deutsch for German); past five entries the list becomes a drop-down. A saved language whose pack has gone falls back to Auto. Picking one reloads the page and sets the language cookie that the chat reads too. English keeps the page in English. Auto walks the browser's languages in order and takes, for each, its exact tag, then its plain language or a regional pack of it (`pt-PT` reaches `pt-BR`); an English entry ends the walk in English. A chosen language that no pack serves falls through to the browser's languages the same way. Card data, such as titles, texts and names, values inside a translated message, such as an error reason, and everything the API returns stay as written.
- **The chat** uses a pack's chat texts, picked the same way as the page, so the board and the chat speak one language when both have a pack for it. Chainlit's own buttons follow when Chainlit ships that language or a pack carries them, and are in English when neither does.
