# Extending Skopax

Writing your own plug-in, from the example in `examples/hello-plugin` to the full contract. Two fuller examples sit next to it; see [More examples](#more-examples).

## The example plug-in: Hello

[`examples/hello-plugin`](../examples/hello-plugin) is a complete plug-in that you can install, test and ship as a layer image. Its [README](../examples/hello-plugin/README.md) lists the files; this page walks through them one at a time. Hello asks one address on a schedule. When the address does not answer HTTP 200, Hello opens a card, and the card clears once the address answers 200 again. Each file shows one part of the contract, and [Writing a plug-in](#writing-a-plug-in) below covers the whole contract.

### `pyproject.toml`: the package and its entry point

```toml
[project.entry-points."skopax.plugins"]
hello = "skopax_hello:PLUGIN"
```

- Skopax finds installed plug-ins through the `skopax.plugins` entry point group.
- The entry point's value names the module and the `Plugin` object in it.
- The example builds with `uv_build`. Any PEP 517 backend works, as long as the wheel carries the package's data files (`icon.svg`, `panel.js`).

### `skopax_hello/__init__.py`: the plug-in

- **Imports.** The plug-in imports only the public surface: `skopax.contract`, `skopax.kit`, `skopax.remote`, `skopax.messages` (only `msg`) and a few more. It opens no sockets and does not import `urllib.request`, `http.client`, `httpx` or `requests`. Every request goes through the transport Skopax hands out, which holds the proxy, the timeouts and the size limits. The test suite checks both rules for built-in plug-ins and for this example.
- **`Plugin(...)`.** The metadata is:
  - `id`, `name`, `version` (`X.Y.Z`);
  - `category` (one of the contract's `CATEGORIES`);
  - `description`, `icon`, `author`, `licence`;
  - `core`, the range of Skopax versions the plug-in works with, as a PEP 440 specifier such as `>=0.5,<0.8`.
- **The `core` range and release candidates.** A release candidate counts as the release it leads to: Skopax `0.1.0rc1` is checked as `0.1.0`, so `>=0.1,<0.2` loads on it. A range that names a pre-release itself, such as `>=0.1.0rc2` or `==0.1.0rc1`, is compared with the full version, pre-releases included. A plug-in whose range does not match is listed under "+ Add integration" but cannot be set up, and the reason names the installed version.
- **Plug-ins that declare `<0.6`.** Third-party plug-ins whose `core` range ends at `<0.6` are refused by 0.6.0 until their range is raised; the Admin notices strip names each refused plug-in.
- **`fields`.** One required field, `Field('url', 'URL', 'url', required=True, help=...)`. An admin adds an instance in Connect > Integrations and fills in the field, and the code reads it as `ctx.instance.config['url']`. A plug-in can have many instances, and each one runs the checks with its own values.
- **`capabilities`.** `Capabilities(hosts=('@url',))` declares the hosts the plug-in talks to. Here that is the host of its `url` field.
- **`problem(ctx)`.** It calls `call_page(ctx.http(), url, timeout=10)`, which reads the address as a page and returns its HTTP status. A 404 or a 503 comes back as a status, and redirects are not followed. An `HttpError` from another transport is read for its code, and an `Unreachable` means no answer. The function returns `None` on a 200, and otherwise a short text such as `https://shop.example.com/health answered HTTP 503`. Every text shows the address through `shown(url)`, without its query or fragment: the card, the section row, Test connection, and the card's short line that Slack posts use. A token in a health URL therefore never reaches a card, the page or Slack. The request itself still uses the full URL.
- **`test`, the Test connection button.** It wraps the work in `kit.connection.result(ask)`. That times the call, keeps the summary that `ask` returns, and turns an error into a short fixed text without the exception's own message. To show your own text, raise `SourceDown`, which is what Hello does.
- **`checks`, the check.**
  - It is declared as `Check('hello', 'Hello address', 300, 0, ('hello',), run, sections=('hello',), section_help=...)`: id, label, period in seconds, offset, the `ran` keys, and the function.
  - `run(ctx)` returns a `Sweep`.
  - Its `PassResult('hello', True, 'ok', cards, {}, ('hello',))` lists the cards found. Each card is a dict built with `anomaly(...)`. Its severity is `crit`, `high`, `warn` or `info` (`SEVERITIES` in `skopax.contract`); `high` is new in 0.5.9 and means users feel the problem now, and a plug-in that sends only `crit` and `warn` needs no change. `alert_sev(label)` turns an alert's `severity` label into one: `critical` maps to `crit`; `warning`, `high`, `major` and `error` to `high`; `low` and `minor` to `warn`; anything else, or no label, to `info`.
  - The card key is `hello|<host>`. `card()` sets `x['key'] = f'{ID}|{host}'`, so the key starts with the plug-in's id, as the PMM plug-in's keys start with `pmm|`.
  - Why a plug-in scopes its keys: card keys are global across every plug-in in the state. Skopax adds the instance segment to a key, but never the plug-in id. If two plug-ins both wrote `down|<host>` for the same host, their passes would fight over one card, opening and clearing it in turn and flipping its `src`. Start every key with the plug-in's id.
  - The `ran` key `hello` tells Skopax that this pass looked, so an open Hello card that the pass no longer reports is cleared.
  - `Sweep(sections={'hello': [row]})` stores one row per instance under the `hello` section, which the page reads.
  - Skopax adds the instance's name to the card key and the row for every instance but the primary one, so two instances never clash.
- **`panels`, the page.**
  - `Panel('hello', 'panel.js', label='Hello', group='more')` adds a Hello page to the More group of the sidebar.
  - The rules for a page:
    - the tab id may not be a built-in page;
    - the label is 1 to 24 printable characters;
    - a label needs a script;
    - the group is one of `main`, `observe`, `activity`, `connect` and `more`.
  - A panel without a label adds no sidebar entry.

### `skopax_hello/panel.js`: the page script

- Skopax serves the script from the package directory at `/plugins/hello/panel.js`, while the plug-in has an enabled instance.
- The script listens for two events:
  - `skopax:state` carries the whole page state, with the open cards in `state.anomalies` and the check's rows in `state.hello`;
  - `skopax:page` hands over the page's `section` element when the Hello tab opens.
- The script escapes every value before it writes HTML.
- The open-card count uses the same filter as the built-in panels: open, not muted, and not triaged as in progress or handled.

### `skopax_hello/icon.svg`: the icon

The icon is an SVG of at most 20 KB in the package directory, named by `icon='icon.svg'`. It is shown on the Integrations tile and in the sidebar. A plug-in whose icon is missing or is not an SVG does not load.

### `LICENSE`: the licence text

Your own plug-in can carry any licence, including a closed one. Skopax is AGPL-3.0-only, and `NOTICE` adds a plug-in exception under section 7 of the AGPL: a plug-in that works with Skopax only through the documented plug-in interface (the `skopax.plugins` entry points and the contract on this page) does not have to be AGPL. Skopax itself and any change to it stay AGPL.


The example plug-ins are Apache-2.0, so you can copy them freely. The example carries a copy of the Apache License 2.0. `license-files = ["LICENSE"]` in `pyproject.toml` puts it into the wheel (`skopax_hello-0.1.0.dist-info/licenses/LICENSE`), so the wheel can be passed on by itself with its licence. The Dockerfile copies it into the build stage.

### `tests/test_hello.py`: unit tests

- The tests run `run` and `test` with a small fake `Context`, whose `http()` returns a fake transport that answers a chosen status or raises `HttpError` or `Unreachable`.
- They need only `skopax.contract`, `skopax.remote` and the plug-in.
- Run them from the root of the Skopax repository with `.venv/bin/python -m pytest -q -n 0 examples/hello-plugin/tests`. The full suite runs them too.

### Working outside this repository

Skopax is not published to a package index; only its images are. A plug-in in a repository of its own runs its tests against a clone of Skopax at the release it targets, next to the plug-in's folder. From the plug-in's folder:

    git clone --branch v0.7.3 https://github.com/skopax/skopax ../skopax
    (cd ../skopax && uv sync --frozen)
    PYTHONPATH=../skopax:. ../skopax/.venv/bin/python -m pytest -q tests

The layer image installs the plug-in with `--no-deps`, so Skopax is not a runtime dependency of the plug-in wheel: leave `skopax` out of the plug-in's `dependencies`. Anything else the plug-in needs at run time must already be in the Skopax image, as the Dockerfile notes below say.

### `Dockerfile`: the layer image

The Skopax image is distroless, so it has no `pip` and no shell. Install the plug-in in a Python build stage, then copy it into the Skopax image's `site-packages`:

```dockerfile
ARG BASE_IMAGE=ghcr.io/skopax/skopax
ARG SKOPAX_VERSION=0.7.3

FROM python:3.15-slim@sha256:65a65fc7b30b06cb6df4930fd4650697cb23f4c2698ab81fc87e4b031bc36928 AS build

WORKDIR /src
COPY pyproject.toml README.md LICENSE ./
COPY skopax_hello/ ./skopax_hello/
RUN pip install --no-cache-dir --root-user-action=ignore --no-deps --target /plugins .

FROM ${BASE_IMAGE}:${SKOPAX_VERSION}

COPY --from=build /plugins /usr/local/lib/python3.15/site-packages/
```

```sh
docker build --build-arg SKOPAX_VERSION=0.7.3 -t skopax-hello examples/hello-plugin
```

- `BASE_IMAGE` (default `ghcr.io/skopax/skopax`) names the Skopax image to build on, for example a mirror or your own registry. `SKOPAX_VERSION` (default: the current release) picks its tag.
- Pin `SKOPAX_VERSION` to the release you run, and keep the plug-in's `core` range in step with it.
- `--no-deps` keeps the layer to the plug-in alone. Anything else the plug-in needs must already be in the Skopax image, or be installed in the same way.
- Start the layer image exactly like the Skopax image (see the [quickstart](../README.md#quickstart)).
- When you start it without a browser, for example in a CI job, set `SKOPAX_ADMIN_EMAIL` and `SKOPAX_ADMIN_PASSWORD` so that a first admin exists. Until one does, every API route answers 503, even with the bootstrap token `SKOPAX_TOKEN`.
- The plug-in is found through its entry point, so `SKOPAX_PLUGINS` is not needed. Connect > Integrations lists Hello, and `GET /api/admin/plugins` lists it with the id `hello`:

```sh
curl -fsS -H "Authorization: Bearer <the SKOPAX_TOKEN value>" http://localhost:8080/api/admin/plugins
```

- The icon is served at `/plugins/hello/icon.svg`. `panel.js` answers 404 until the plug-in has an enabled instance.

## Writing a plug-in

A plug-in is a `Plugin` object from `skopax.contract`. This section covers what it can use and declare besides the page panels described under [Plug-ins](plugins.md#plug-ins).

### Imports and the kit

A plug-in module imports the standard library, third-party packages, its own package and, from Skopax, only `skopax.contract`, `skopax.kit`, `skopax.clock`, `skopax.remote`, `skopax.redact`, `skopax.monitor`, `skopax.errkind`, `skopax.kube`, `skopax.agent`, `skopax.mail` (the shared mail sender, see [Mail server](plugins.md#mail-server)), `skopax.severity` (the shared severity rules), `skopax.tags` (the card tags and their names) and `msg` from `skopax.messages`. None of these imports a plug-in, and a test holds the built-in plug-ins to this list.

A plug-in reads the network only through `ctx.http()` and the kit. Pinned TLS (`ca-pinned`) is for the core transport only: a plug-in reaches a pinned server through the transport core hands it (`ctx.http()`, built on `remote.sender`), never with a TLS context of its own, and event-loop TLS on a pinned context is refused. A plug-in that calls a service outside an instance, such as a settings source, and must trust a certificate authority of its own builds its transport with `remote.pem_sender(pem, follow=False)`, which verifies against that PEM text (the Vault plug-in does this for `VAULT_CACERT`). A JSON read through `ctx.http()` has a wall-clock limit of twice its timeout, as a page read has, and reads at most 64 MB; a plug-in can set a smaller cap with `call(..., limit=<bytes>)`. Past either limit the read fails as unreachable, naming the address without its query and the cap. A refused read raises `HttpError`, whose `code` and `body` (the first 4 KB) were always there; its `headers` now hold the answer's headers with lower-case names, such as `retry-after`, `x-ratelimit-reset` or a redirect's `location`, and are empty for an error built without them. The repository's guard tests refuse socket, HTTP-client, subprocess and dynamic-import use in plug-in code, including transport names re-exported by core or kit modules; they catch mistakes and are not a sandbox, since plug-ins are code an admin chose to install.

`skopax.kit` holds the helpers that several plug-ins share:

- `kit.promql`: the Prometheus HTTP client (`Prometheus`, `client_for`, `ranged` and the query helpers), `bounded(transport, seconds)` with its `Late` error for a pass budget, `instant(peer, expr)` for Test connection, and `ui_of`, `graph` and `number`;
- `kit.grafana`: the Grafana datasource client. `Datasource(url, token, transport, name, timeout=20, limit=None)`, or `client_for(info, name, transport)` for a Grafana instance, finds the datasource once in `GET /api/datasources` (`uid()`, or `find(listed, name)` on a list already read: by name, a Prometheus-type one first, then by uid) and queries it through `/api/datasources/proxy/uid/<uid>/api/v1/` with `data`, `result`, `vec` (finite values only) and `span`; `limit` caps the answer in bytes. A failure is a `DatasourceError` with `reason`, `code`, `right` (the missing `datasources:read` or `datasources:query`), `said` (the datasource's own error text) and `late` (the request timed out). `explore(ui, uid, expr)` links to Grafana Explore. The managed Redis example reads through it;
- `kit.links`: `sendable(url)`, whether a webhook or link address can be posted to: `https`, a host, no user name or password, no space, control or non-ASCII character, a valid port and at most 2000 characters; core's routes and the Teams plug-in share it;
- `kit.text`: `duration(seconds)`, and `cut(text, limit)`, which folds whitespace and masks secrets before it cuts;
- `kit.connection`: `result(run)` for Test connection;
- `kit.env`: `env_set`, for `env_instances` (see [Peers, clients and state](#peers-clients-and-state));
- `kit.access`: the refused-read helpers: `denied(code)`, `card(check, plugin, part, permission, status, credential)` for the warn card, `ran_key(check, part)`, `text(plugin, part, permission, credential, status)` for tool errors, `tested(plugin, part, status, permission, credential)` for Test connection, and `status(base, parts)`. `card` also takes `name` (the part as people read it, while the keys keep the part id), `plural` (for a plural credential such as keys) and `what` (the plug-in's own explanation). An empty credential means none is set. `kit.promql.credential(config)` names a Prometheus credential (`password` for basic auth, `token` for a bearer token, empty for none). Use `kit.access` for every refused read;
- `kit.elastic`: the Elasticsearch ES|QL client and its helpers (`client_for`, `Elastic`, `ElasticError`, `Budget`, `refusal`, `access_card` and `fields_card` on top of `kit.access`, `no_access` and `discover_for`), for plug-ins that read through an Elasticsearch instance;
- `kit.alerts`: `QUIET_ALERTS` (alerts that are never a card) and `ALERT_KEEP` (the alert labels a card keeps), which Prometheus and Grafana share;
- `kit.web`: the page reader for a site's own pages (`Site`, `PageCheck`, `site_pacer`, `host_of`, `public_host`, `refusal`, `suffix_entries`), which opens only the site's hosts and connects to the address it checked;
- `kit.options`: helpers for options an admin types into a field: `entries(raw)` and `pairs(raw)` (comma-separated `key=value` entries, with the ones it cannot read named), `number(text)`, and `compiled(raw)` with `search(pattern, text)` for an admin's pattern, which compiles only a pattern of at most 200 characters and matches the first 400 characters of a text within 50 ms (a slow pattern reads as no match). A field of kind `regex` is already checked when it is saved; use these where the pattern is applied;
- `kit.browser`: the client of the browser service (`Browser`, `Shot`, `BrowserDown`);
- `kit.google`: Google service-account sign-in (`GoogleAuth`, `access_key`, `bounded`, `connection_test`) and its refusals (`GoogleError`, `access_card`), shared by the Google plug-ins;
- `kit.umami`: the Umami client (`Umami`, `UmamiError`, `form_of`, `top_paths`), shared by Umami and the page scan;
- `kit.nearest`: `closest(wanted, names, limit, key)`, the names most like what was asked for, which the GitHub and GitLab tools use to suggest nearby files and tags;
- `kit.releases`: `attach_publish`, which names the latest Tag Manager publish on a drop card;
- `kit.flags`: `scan(tool, text)`, the phrase scanner core runs on tool output and on model calls. Core's `card` and `past_cards` answers are scanned like any tool output. In `past_cards` the fields only Skopax or the investigator write are left out of the scan: the outcome label, the run recap, the answer of each earlier ask, and a mute reason Skopax wrote itself (a mute or known noise with no reason typed, or one carrying exactly the text the page, the board or a chat answer fills in when nothing is typed, marked or not), so a past card marked as known noise does not hold the run's posts. A note, a reason a person typed (even one that only starts like Skopax's sentence), the question of each ask, what people said in Slack, every other field and every log line, ticket or page are scanned as written. `past_cards` answers with short digests by default: the first line of the investigator's own note is left out of the scan like its note, and a person's verdict (resolve reason, Known noise or mute reason, ticket) is scanned as written. A `detail` call returns one whole occurrence and is scanned like a full row. `past_runs` answers are scanned too, the earlier answer and its searches apart from the rest, like a run recap. In the brief, the note of a person's earlier verdict is scanned apart from the card text, so only the hard phrases flag in it; the saved card keeps only the newest verdict's kind, who and when. In the brief, the answer line of an earlier Slack ask is left out like the outcome. A refusal caused by planted text (no cause, no business tag, no absorb pattern, no post to the main channel, no Slack message) is marked held on the tool call, and an argument the model sent outside the tool's schema (a name that is not one of the declared choices, a wrong type) is marked refused input; the Tools page counts both apart from errors. A one-off task after start, in the background, marks the mutes and past cards marked earlier. A standing mute entry is marked only when a done action of the same kind has exactly its key or pattern, was applied within 60 seconds of it, took no typed reason (no reason, a Slack click with no reason in its call, or an action applied from a chat answer), and the entry's reason is exactly the text that action wrote (the page's known noise or mute text, the chat text, or the Slack click text); an entry a later duplicate wrote ("follows #n") is never marked. A past card is marked when the live mute entry that covers its key today, found as a pass finds it, is marked and shows the same reason. A failure, or a mute list that changed while the marks were written, leaves the task unfinished and the next start tries again; any other past card is scanned whole; `open_cards` instead shows a card whose text trips the scanner as held, so one planted card does not hold every run's posts.

For Test connection, write a function that makes one real call and returns a short summary, and return `connection.result(that_function)`. It times the call and turns a failure into a fixed sentence: credentials refused (HTTP 401), credentials that lack a permission (HTTP 403), another HTTP status, a TLS failure, a timeout, a service that cannot be reached, or a failed test named by the error's type only. A `SourceDown` keeps its own text, and a `ReadError` its message with known secret shapes masked. The exception's own text never reaches the page, because it can carry a URL with a token.

`ctx.instance.off_checks` (a frozenset of check ids) names the checks switched off on the instance, in a pass and in Test connection, so a test can leave out the parts only those checks read. Test connection on an unsaved form uses the form's ticks; otherwise it uses the stored ones, and it is empty when there are none.

### The instance form

Connect > Integrations builds the form that adds or edits an instance from `fields`, in the order they are declared. Two `Field` options shape it, and both default to the plain form:

- **`group`** names the section a field sits in. Fields without one come first, under no heading. Each group then gets a section, in the order its first field appears, headed by its id with a capital first letter (`sign-in` reads Sign-in). `group='advanced'` puts a field in a folded Advanced section at the end, and `pem` fields always go there. Advanced opens on its own when one of its fields holds a value other than its default or a stored secret, or when a save refuses one of its fields. A group is empty, `advanced`, or a lowercase id that starts with a letter and has at most 24 letters, digits and hyphens. Group every field of a plug-in or none: ungrouped fields move above the first heading.
- **`choice_labels`** gives readable names to the values of a `choice` field, such as `{'none': 'No sign-in', 'header': 'Token in a header'}`. Each key must be one of `choices`, and each label is 1 to 40 printable characters. A value without a label is shown with a capital first letter and spaces for underscores (`header` reads Header). Only what the form shows changes: the stored and sent value stays the choice.

A third option checks a value when it is saved:

- **`check`** is a function that gets the typed value of the field (text, as the form sends it) and answers None (or an empty text) when the value is fine, or a sentence that says what is wrong, such as `Field('selector', 'Selector', 'text', check=lambda v: None if v.startswith(('#', '.')) else 'A selector starts with # or .')`. Saving the instance in Admin then refuses the value with that sentence under the field; it is flattened to one line and cut at 200 characters, and a secret field's own value in it, as typed or with its whitespace flattened, shows as `***`; when 8 or more characters of the secret still show in the 200 characters kept, core's own sentence is used instead. Core reads only the first 800 characters of the answer (plus the length of the secret). Core asks only for the values a save sends that are not empty, after its own checks of the field's kind, so an unchanged or cleared value is not asked again; instances from the config file, the environment or a settings source are not asked. A check gets 5 seconds; one that is late, raises or answers anything other than text or None refuses the value with core's own sentence ("could not be checked by its integration" or "was not checked in time"), never with the error, which goes to the log by its type only. A save of the same field while a late check still runs is refused at once, and a slow check holds no other save. Anything other than a function or None breaks the plug-in.

Two more options turn a text field into a searchable picker:

- **`suggest`** is a function that gets a `SuggestContext` and returns the values to pick from, as a list of plain texts in the order to show them (the plug-in may cache them), or a `Suggestions(values, note)` when the page should also show a short note, such as that only part of the list was read. The context has `values`, the field values of the form with secrets resolved exactly as Test connection resolves them (a typed secret, else the saved secret of the instance being edited, never another instance's, and never after the form moved the address the secret belongs to), `transport`, the plug-in's transport with its allowed hosts, and `deadline`, a `time.monotonic()` value by which the answer must be back. Only `text` and `url` fields may suggest; anything other than a function or None, or a suggest on another kind, breaks the plug-in. Raise `Refused('Enter the API token first')` (or a `ReadError` with a 4xx status) to answer with your own sentence; any other error is named by its type, or as a transport failure, like Test connection names it.
- **`separator`** is `''` (the field holds one value), `','` or `';'` (the field holds a list joined by it). The form shows a list as removable chips above the search box and stores the chosen values joined by the separator and a space; a value it was given that is not changed is sent back exactly as it was.

The page asks for the list the first time the search box gets focus, with `POST /api/admin/plugins/{plugin}/fields/{key}/suggestions` and the same body as Test connection (`values` and an optional instance `name`). The route is for admins, refuses a cross-site request like the other admin posts, runs the function off the event loop for at most 10 seconds and answers `{"values": [...]}`, plus `note` (at most 200 characters) when the plug-in gave one. It keeps the plug-in's order, drops values that are not texts, are empty after trimming, are longer than 200 characters, are not printable, hold the separator or a resolved secret, or repeat an earlier one, and keeps at most 2000. A refusal answers 400 with `{"detail": ...}`, a saved secret that must be typed again because the form moved its address 422 with the field and "Re-enter <field> to load the list", a failure, a late answer or an answer that is not a list 502, an earlier ask of the same field that still runs 409, and an unknown field or one without `suggest` 404; a resolved secret never shows in a detail, which is cut at 300 characters. A refusal is not kept: the next open asks again. Filtering is done in the page, ignoring case and accents, and a typed or pasted value that matches a list value that way is stored with the list's spelling. Text typed into the box is kept when you press Enter, Save or Test connection (split by the separator); leaving the box keeps the text without adding it. A value that is not in the list is marked "not in the list", so a plug-in whose list fails still lets you fill the field.

The admin listing serves `group` and `choiceLabels` with each field, and `suggest: true` with the `separator` for a field that suggests. A `bool` shows as a switch and still submits `true` or `false`. A `choice` with two or three options, counting the empty one of a field that may stay empty, shows as segments that the arrow keys move through, and a longer one as a list. A `secret` has a Show button for what was typed and a chip that says it is set and where it comes from. Test connection, Cancel and Save stay at the bottom of the drawer while the form scrolls. A plug-in whose labels or group break these rules does not load, with a reason that names the field, as for any other field rule.

### The setup guide

`setup=Setup(steps, docs, docs_label)` tells an admin how to create what the plug-in needs, such as an API key or a service account. Connect > Integrations shows it in the plug-in's side panel, in a folded "How to set it up" section right under the description and the version line. The section is open while the plug-in has no instance and closed once it has one, and it shows for built-in and custom plug-ins alike. A plug-in without `setup` (the default, None) shows nothing.

- **`steps`** is a tuple of 1 to 10 texts, each non-blank, printable and at most 400 characters. They are shown as a numbered list, as plain text: no markup or link in a step is interpreted.
- **`docs`** is empty or an `https://` link of at most 500 characters with no whitespace, best the vendor's official guide. It shows as a link that opens in a new tab with `noopener noreferrer`.
- **`docs_label`** is the link text, at most 60 printable characters; the page shows "Setup guide" when it is empty. It needs `docs`.

A plug-in whose setup breaks these rules does not load, with a reason that says so, as for any other rule. The admin listing serves it as `setup` (`steps`, `docs`, `docsLabel`), or null.

### Company knowledge

`company_knowledge` marks a plug-in as a source of company knowledge, such as runbooks, postmortems and design docs. It is a text:

- `''` (the default) is not a knowledge source.
- `'always'` is always one. The plug-in decides when it has anything to offer: Confluence, for one, offers its tool only once its Spaces field is set.
- The key of one of the plug-in's own fields makes it a knowledge source for each instance where that field is set, such as `company_knowledge='docs'` for a plug-in with a `docs` field.

Any other value breaks the plug-in, with a reason that says so. Connect > Integrations shows a tile of a knowledge source in its own category with a Knowledge badge (Knowledge, Knowledge off or Knowledge needs setup, with a tooltip saying why), and the Knowledge chip lists exactly those tiles; "+ Add integration" marks the entry with the badge too. The admin listing serves it as `companyKnowledge`.

`knowledge_also=True` says knowledge is a second role of a plug-in whose main job is something else, such as Jira (tickets) or GitHub (code). It needs `company_knowledge` set; any other value, or `True` without `company_knowledge`, breaks the plug-in. Every knowledge source shows the same badge and sits in the Knowledge chip; the flag only records the plug-in's main role. Pure sources such as Confluence leave it `False`. The listings serve it as `knowledgeAlso`.

`corpus` makes a plug-in a source of pages for Search by meaning. It is a `Corpus(list, read, max_pages, spaces=None)`: `list(ctx, since)` yields a `DocRef` (id, title, url, modified, space) for every page changed since the given time (all pages when it is empty), `read(ctx, id)` returns a `DocText` (title, url and text, already redacted), `max_pages` caps one listing (1 to 100000), and `spaces(config)` returns the spaces the instance allows. A listing that stops early raises `Truncated`, so nothing is deleted on it. The plug-in needs a bool field `index-pages`; pages are indexed only on instances where it is on.

### Peers, clients and state

- **Peers.** A plug-in that reads through another plug-in's connection, for example a check that queries a Prometheus, names it in `uses` and adds a field of kind `instance` whose one choice is that plug-in: `Field('source', 'Prometheus', 'instance', choices=('prometheus',))`. Admin shows the field as a list of that plug-in's instances, and saving refuses a name that is not one of them. At run time `ctx.peer('source')` gives that instance (`info`) and a transport to it (`http()`), and `ctx.peers('prometheus')` lists every runnable instance of a used plug-in, primary first. The other way round, `ctx.users()` lists the instances that read through this one: the enabled, runnable instances of other plug-ins whose `instance` field picks it, as `InstanceInfo` with their non-secret values only (Elasticsearch uses it to let the investigator's ES|QL read the indices those instances name). If the peer is switched off, deleted or parked, only the reading instance's pass fails, with a text that names the peer. A used plug-in that is missing or broken never stops the reader from loading. A peer also carries `off_checks`, the checks an admin switched off on that instance. A plug-in that skips work because a peer covers it skips only while the peer's own check is on: Grafana skips a datasource of a Prometheus instance, and Kafka leaves out that instance's namespaces, only while its `prom` check is on (Kafka also needs its `kube` profile). When the check is switched off they raise the cards themselves, and when it is switched on again their copies close at their next pass.
- **Through an agent node.** A service that only a Kubernetes agent can reach, such as a test cluster or a dev back office, is still an ordinary instance of your plug-in: the agent only relays. Declare an `AgentRead` and give it `node_keys`, which maps the instance's own fields to the agent keys the read declares, such as `node_keys={'url': 'shop.url', 'client-secret': 'shop.secret'}`, or a function that takes the instance's config and returns those keys (Elasticsearch uses one so that the APM cluster falls back to the log cluster). Core then adds the field `via-node` (Through agent node, in Advanced) to the plug-in's form. It must name a Kubernetes instance in mode `agent` that is on and has no problem; any other name is an instance problem shown in Admin, and the instance does not serve until it is fixed. Changing it asks for the instance's secrets again, as a changed address does. In a tool or a check, call `ctx.node_read(op, args)`: core takes the instance's node, maps its config with `node_keys` (empty values are left out, and only keys the read declares are sent), pushes that config to the node with `PUT /api/agent/sources` under the read and the instance name, and sends the read with the instance name. The node keeps one pushed config per read and instance, in memory only: nothing is written on the node, and after a restart the next read is answered 503 and core pushes again. When an instance moves to another node or is deleted, core pushes an empty config for it to the old node at its next refresh, which clears it there; Test connection on a form not saved yet uses a one-off name that is cleared when the test ends. A read without an instance name, as an older server sends it, uses the node's own config of that read, so the agent fields set on the Kubernetes instance serve those reads; an agent built before this that ignores the instance name keeps one config per read, so core pushes again whenever it switches instances and runs the reads through that node one at a time. An instance with a node runs none of the plug-in's checks, and Admin says so in its health line and shows no check boxes for it; `probe_targets` should return nothing for it, since core cannot reach its address. `ctx.node_read` on an instance without a node raises `ReadError`, so a plug-in reads `via-node` itself to pick between its direct client and the node.
- **Clients.** `client(info, transport)` builds one client object for an instance. Core features that use an integration reach its connection through it, and `ctx.client()` hands the same object to the plug-in's own checks and tools. It is built on first use and kept until the instance's values change. A client that fails to build is tried again after a minute, or as soon as the values change. While no instance serves, core reads the integration as not set up or switched off.
- **Limits.** `max_instances` caps the instances; see [Instances](plugins.md#instances).
- **Environment.** `env_instances(env)` turns environment variables into instances named in the environment source. Use `kit.env.env_set(env, plugin, needed, optional)`: it returns the stripped values when every needed variable is set, and for a partial set returns None after one log warning naming what is missing.
- **Capabilities.** `Capabilities(hosts, secrets)` lists the hosts a plug-in may call, as fixed names (`api.atlassian.com`) or `@<field>` for the host of a field's value, and the fields that are secrets.
- **Missing and refused.** A client raises `contract.Missing` for a 404 that core reads as "not there", and `contract.Refused` for a write the service refused with a sentence the page shows.
- **Code hosts.** A plug-in whose client core uses for deploy enrichment and code links returns a `contract.CodeHost` from `client()`. Core asks the code hosts it knows, GitLab and then GitHub, and a repository resolves on the first serving host that knows it; every later read and link of that repository goes to the same host. While two hosts serve, a host that cannot answer makes the repository undecided (`codehosts.Undecided`, a `SourceDown`) instead of letting a later host answer, and deploy enrichment skips that one deploy without marking it. A repository dict needs `id`, `web`, `path` (whose last part is the service name), `full` and `branch`, and commits use GitLab's field names (`id`, `title`, `message`, `author_name`, `committed_date`, `parent_ids`), as `plugins.github` does for GitHub.
- **Refusals.** A client that core features use raises `contract.Denied(text, part, permission)` for a read the service refuses. It is a `SourceDown`, so every handler that catches one still does, and an `errkind.NoAccess`, so core names the part and the permission (deploy enrichment, the `jira-links` pass, the deploy report) instead of reading the refusal as nothing there.
- **State.** In a check run, `ctx.previous(section)` returns the rows this plug-in wrote to that section last time for this instance, `ctx.deploys(since)` the recent deploys, `ctx.open_cards()` the check's own open cards for this instance (`plugin_wide=True` for every check of the plug-in), and `ctx.last_status()` the status this check stored for this instance at its last pass, or None. They read the state once, at the start of the run. A tool can read `ctx.previous` too.
- **Memos.** A check can return `Sweep.memos`, a dict of small JSON documents (at most 200 per pass, each at most 4 MB) that core keeps outside the state for that instance, and read one back with `ctx.memo(key)` in a later run or in a tool. A memo nobody writes for 90 days is dropped. A plug-in gets no other database of its own.
- **Per-run state.** `ctx.run_state` is a small store that lives for one run and is dropped when the run ends: one check run (one instance, one pass), or one investigator run, where every call of the plug-in's tools in that run shares it. `get(key, default=None)`, `put(key, value)` and `count(key, by=1)` (adds and returns the new total; `by=0` only reads) take a key of 1 to 200 characters; a count on a key that holds something else raises `ValueError`. It keeps at most 500 keys, and the oldest give way to new ones; a value must be JSON data (dicts with text keys, lists, texts, numbers, true, false, null), is stored as a copy (a tuple comes back as a list), and one larger than 64 KiB once written as JSON is refused with `ValueError`, as is anything that is not JSON data. Each plug-in has its own store in a run, two runs never share one, and it is safe to use from several threads. Use it to count sub-calls against a budget or to cache a read within the run; a value that must outlive the run belongs in a memo.
- **Model calls.** In a check run, `ctx.ai(model)` gives a client whose `complete(system, messages, max_tokens, schema=None, effort='medium')` returns `{text, usd}`. The call goes to the provider of the plug-in's model, and never to another provider. It is None without a working key for that provider, for a model with no price, while the investigator is switched off or stopped, or once the daily spend cap is reached, and each call checks that again and returns None when it is. Every call is counted in the daily spend and in the spend ledger under `<plug-in>.<check>`; the Website page scan's calls go under `pagescan`, which the Costs page lists. A failed or refused call raises `ReadError` with a fixed reason.
- **AI providers.** `skopax.ai.register_provider(prefix, factory, capabilities, models=None, company=None)` adds a provider whose model refs read `<name>/<model>` and whose provider id is `<prefix>:<name>`; the built-in OpenAI-compatible connections use it with prefix `compat`. `factory(name, timeout, retries)` returns an adapter (with `turn`, `once`, `provider`, `bad_request` and `api_error`) or None when that name has no working connection; it is called on every key check, so it caches its client. `capabilities` is a subset of `tools`, `images`, `web_search`, `thinking`, `cache` and `fallbacks`, or a function of the provider id; without `thinking` or `fallbacks` the adapter's `turn` gets `thinking=` and `fallbacks=` keywords to ignore. `models()` lists the refs Admin offers, and `company(ref)` names where the data goes. Register once at start; `unregister_provider(prefix)` removes it.
- **Screenshots and posts.** A check can return `Sweep.shots` (images with the card key they belong to, at most 20 per pass, counted against `screenshot.max-per-day`) and `Sweep.posts` (at most 3 digests per pass, each a title, card lines and picture replies, in plain text). Core stores the shots and shows them on their cards, and posts a digest to the main Slack channel once the pass is applied: it escapes the text, links each card, leaves out quiet and already posted cards, marks the rest posted and puts the pictures in the thread, at most 8 per thread. Nothing is marked posted while Slack is not set up.
- **Cardless digests.** A check can return `Sweep.digest = Digest(title, lines)`, a summary that belongs to no card, such as a weekly report. Once the pass is applied, core posts it to the main Slack channel as one plain message: the title (or the plug-in's name), then one bullet per line. Core escapes the text, so a mention or a link in it stays plain text; flattens each line, drops blank ones and posts nothing when no line is left; keeps at most 50 lines per pass (one warning names the rest), cuts the title at 300 and each line at 500 characters at a word, and ends with "and N more" when the message would pass 3000 characters. It posts at most one digest per check and instance an hour, so the check decides the cadence (its `period`, or a memo that says when it last wrote one) and core only stops a check that returns one on every pass. A digest is not sent while Slack is not set up or while Admin > Features > Slack auto-send is off (on by default; the card digests of `Sweep.posts` do not follow that switch), and a pass that fails or is not applied sends none. Each digest shows in Activity as a `check-digest` action, done or failed. A digest can name card tags, `Digest(title, lines, tags=('infra', 'data'))` (empty by default): it is then also mailed to the responsibles of those tags (see [Card tags and responsibles](setup.md#card-tags-and-responsibles)), one mail per person even when they look after several of the named tags, while a Mail server is on and Mail responsibles their part (`tags.mail`) is on, also while Slack is not set up or auto-send is off. The mail's subject is "[Skopax] " and the digest's title, cut at 300 characters at a word and at the 200 a subject holds, and its body has the same lines with the same limits as the Slack post (50 lines, 500 characters a line, "and N more" past 3000 characters); the HTML part is escaped, so a tag or a link in the text stays plain text, and an Open the board button leads to the board's Open view. Unknown tag ids are left out with one warning per check, and a digest with no tags is posted to Slack only. At most one digest mail goes out per check and instance an hour, counting one that failed, and each shows in Activity as a `check-digest-mail` action, done, or failed when no mail went out. Anything other than a `Digest` of a text title, a tuple of texts and a tuple of tag ids fails the pass.
- **Notes on clear.** A check can return `Sweep.cleared = {card_key: Cleared(note='', outcome='')}` for the cards it clears in that pass, keyed as it raised them, such as `Cleared('Rolled back to 1.4.2', 'fixed')` when it fixed the cause itself. A note is flattened and cut at 500 characters at a word, and is kept on the card as `clearNote` (`text`, `by` the plug-in's name, `plugin`, `at`, and `outcome` when the plug-in resolved the card): the opened card shows it under Cleared, the card's history keeps it for the year the history lasts, and the `past_cards` tool returns it in a `detail` call. `outcome` is `fixed` or `handled` (no action needed); it resolves the card as core's auto-resolve does (`triagedBy` `auto`, `resolution` `{kind, by: <plug-in name>, via: system, at}`), so the history records it as Fixed or No action needed by the plug-in. Only a card this very pass cleared takes either: a card still firing, cleared by an earlier pass, closed as stale or retired, of another instance or another plug-in, or unknown is left alone. A note is added whatever the card's triage, but an outcome only replaces no triage or an investigated one; a card a person, the investigator or a ticket has taken or resolved keeps that. In Slack the plug-in's words go into core's own clear note, so a card gets one note per clear, under the same rules: only while `slack.clear-note-minutes` is above 0, after that many minutes of quiet, and only for a card whose post belongs to this occurrence and that is not muted. On a note-only clear the note opens with the plug-in's text in place of "Back to normal" and keeps core's Resolve hint and button (and, for a kind of problem that comes back, core's warning that it does not fix itself). With an outcome the note says "Fixed by <plug-in>" (or "Resolved by <plug-in>, no action needed") followed by the text, with no Resolve hint, since the card is already resolved. The card keeps `clearNote` whatever the setting. A card that opens again drops the note. At most 200 entries per pass count (one warning names the rest); anything other than a dict of card keys to `Cleared`, or an outcome other than these two, fails the pass.
- **Releases.** `releases(rows, since)` gets the plug-in's own section rows, one instance at a time, and returns release rows, such as Tag Manager publishes. Each row needs the text keys `ns`, `svc`, `at` and `toImage`, and may carry `id`, `fromImage`, `title` and a small dict under the plug-in's id. Core cuts long texts, drops rows older than `since`, sets `kind` to the plug-in's id and lists the rows beside the deploys: under Releases, in `GET /api/deploys`, in the investigator's `deploys_since` and in `ctx.deploys`. They are never stored as deploys, so the post-deploy check never sees them. All `releases` calls of one read share the 10 seconds of the other hooks. A call that fails, runs late or returns something other than a list leaves that plug-in's rows out of the read, with one log warning until it works again. Rows of an instance other than the primary carry its name as `cluster`.
- **Deploy report.** `deploy_report(ctx, deploys, started_at)` is called for each post-deploy check by the pod that has claimed it, before its report is written, with a copy of the deploys the report covers and the time of the first of them in seconds. It returns None to add nothing, or `{'wait_until': float | None, 'text': str, 'flags': list[str]}`: `text` is not blank and is cut at 2000 characters, `flags` holds at most 10 texts of at most 100 characters, and `wait_until` is a time in seconds or None. Core adds each `text` to the report under the plug-in's id (`plugins`), adds each flag as `<plug-in name>: <flag>` to the report's `flags` and its brief, which turns the brief to a warning, and to the Slack post text, and appends the text to the report text. When an answer has a `wait_until` that has not come yet, the check hands its claim back, keeps its request open and calls the hook again every 2 minutes, and the report is written at the latest `wait_until` or 30 minutes after the check was requested, whichever is earlier. Only that report waits: the checks requested after it are written in the meantime. A claim that cannot be handed back writes the report at once. A hook that raises, answers anything else than None or this dict, or takes longer than the hook limit (10 seconds, `HOOK_TIMEOUT_S`) leaves the report as it was, and the failure is logged once for the plug-in until its next good answer. Only plug-ins that are serving are asked; the context is that of the plug-in's primary instance.

### Migrations

`migrations` is a tuple of `Migration(version, name, run)`. At start, after Skopax's own migrations, the migrations of each plug-in run in version order, each one once, on one pod at a time (see [Upgrades](operations.md#upgrades)). `run(db)` gets the database. A migration that fails breaks only its plug-in, with a reason that names the migration and the error type, and it is tried again at the next start. A version that appears twice breaks the plug-in before any of its migrations run. A database connection lost during a migration only delays it: it is tried again on each refresh, except at start for a required migration (see below). Write a migration so that running it again does no harm, since one that fails after a write runs again.

- **Instances.** `Migration(..., needs_instances=True)` is called `run(db, writer)`, with a `contract.InstanceWriter`, so that a plug-in can move settings it kept on its own into instances. The writer sees the instances of Admin and of every settings source, and has three methods:
  - `adopt_sealed(plugin, name, field, sealed, by)` puts a value that is already sealed (`enc:v1:...`), such as a secret an older version kept in its own collection, into a field of an existing instance. The value must open with the current secret key and fit the field, which must be of kind `secret` or `text`. A secret field stores it byte for byte, without opening it for the plug-in or sealing it again; a text field stores the opened text.
  - `put(plugin, name, values, secrets, by, primary=False, sealed=None, enabled=True, off_checks=())` creates the instance or changes the one with that name. It checks every value as an Admin save does: an unknown field, a value that does not fit its field, a secret field under `values` or another field under `secrets` is refused. `secrets` are given in plain text and sealed. `sealed` holds values already in the sealed form (`enc:v1:...`) for fields of kind `secret` or `text`; each must open with the current secret key, or it is refused with a reason naming the field and never its value. A sealed secret is stored byte for byte and a sealed text field is stored opened, in plain form, and both count for the required fields, so an instance whose required secret exists only sealed is created in one call. A field given both under `sealed` and under `values` or `secrets` is refused. `enabled=False` stores a new instance switched off, or switches an existing one off; `enabled=True` switches a new one on and leaves an existing one as it is. `off_checks` switches those checks off on the instance, as Admin does; an unknown check id is refused. `primary=True` makes the instance the primary; with `enabled=False`, or for an existing instance that is switched off, it is refused. Without `primary=True`, a plug-in's first instance still becomes its primary, even switched off, as in Admin. Everything is checked before anything is written.
  - `get(plugin, name)` returns the instance's values that are not secret, as a mapping, or None when there is no such instance. It never returns a secret, plain or sealed, so a migration can skip a field that is already set.

  On an agent instance, a key the writer sets for a field of an agent read (such as `elastic.logging-url`) is pushed to the agent and replaces the value of that key in the agent read's own config; once a key is pushed for a read, the agent's own config is no longer used for that read.

  Neither `adopt_sealed` nor `put` writes a field a settings source owns (see [Instances](plugins.md#instances)): that call is refused, as it is in Admin, while the free fields of a source instance can be written. A refused call raises `contract.InvalidInstance` (its `field` names the field) or `contract.SourceOwned` (its `field` and `source` name the field and the settings source), so a migration can catch either; an uncaught one fails the migration. `by` is stored as the author of the change. A migration that moves an old Admin secret into a new instance in one call:

  ```python
  def move(db, writer):
      old = db['shop_settings'].find_one({'_id': 'connection'})
      if old is None or writer.get('shop', 'main') is not None:
          return
      writer.put('shop', 'main', {'url': old['url']}, {}, 'migration', sealed={'token': old['token']}, primary=True)

  Migration(3, 'move-connection', move, needs_instances=True)
  ```
- **Required migrations.** `Migration(..., required=True)` is for a migration without which the plug-in, or what it shares with core, would be wrong. A start never serves while one is not applied, whatever the reason: after the plug-in migrations, Skopax checks every loaded plug-in, also one that is broken at load, locked by its edition or switched off, and stops the start when a required migration is above the plug-in's stored version. So the start stops when the required migration fails, when an earlier migration of the plug-in fails or a version appears twice so that it never ran, when it needs instances and the run has no writer, and when this pod cannot run it because another pod holds the lease past the wait or the database connection drops. The reason names the plug-in and the migration, never the error's text, and a stored version that cannot be read counts as not applied. When the start cannot reach the database at all to run or check the migrations, it stops as soon as any loaded plug-in declares a required migration, naming those plug-ins; without one, the start serves and runs the migrations on a later refresh. The stored version stays where it was, so the next start runs the migration again (Kubernetes restarts the pod; by then another pod has applied it or failed for real), and once it has passed it never runs again. A required migration cannot newly appear without a restart, so on a refresh after the start a failure is only logged, once at error level, and the migrations are tried again on each refresh.

### Hook time limits

Skopax waits at most 10 seconds (`HOOK_TIMEOUT_S` in `skopax.bounded`) for a plug-in's `settings_source`, `entitlement` and `org_validators` hooks and for its `client`. For `links` the 10 seconds cover the whole links step of one pass, not each call: once they are spent, the links still to come are skipped for that pass. The `probe_targets` calls of one probe run share a deadline of 5 seconds. A hook that is slower is skipped for that call, as if it had failed, and its late answer is thrown away; while it still runs, it is not called again. When a main Skopax starts, a settings source that is too slow stops the start, as one that fails does; an agent starts anyway and tries the source again. Later reads keep the source's last data. A `settings_source` that returns `None` supplies no source for that read. `confirm` has its own 30 seconds (see [Tools and proposals](#tools-and-proposals)). `Outbound.post` gets 10 seconds per post, one post at a time per instance (see [Outbound](#outbound)). A post that is late, raises, or answers anything but `ok` true counts as failed, and so does one that finds the instance's previous post still running. Core tries an automatic post again later, and a post by hand answers with the failure. Delivery is at least once: a post that succeeded after the limit can be sent twice. `role_resolver` has its own 5 seconds (see [Sign-in hooks](#sign-in-hooks)).

A `settings_source` hook is called as `settings_source(env)`. A hook that also takes a `field_kind` parameter (as a keyword or a second parameter, such as `def settings_source(env, field_kind=None)`) is called with `field_kind` as well: a function `field_kind(plugin_id, field)` that answers the kind of that field of a loaded plug-in (`'secret'`, `'text'`, `'url'` and so on, agent fields included), or None for an unknown plug-in or field. A source uses it to refuse a value meant for a secret field when the target is not one; the Spring Cloud Config plug-in fills templates only into fields it is told are secret. A hook that takes only `env` gets `env` alone, and a source that does not get `field_kind` should treat every field as not secret. Core always supplies `field_kind` to a hook that declares it, so a hook registered as a `functools.partial` that already binds `field_kind` gets core's function in place of the bound one; bind other arguments only.

### Sign-in hooks

- **`role_resolver(user, channel)`** gives a person's role at sign-in. `user` is a copy of `{email, name, source, role, claims}`: the stored role, if any, and the token's claims (empty in Slack). `channel` is `page`, `mcp` or `slack`. It returns `viewer`, `operator`, `admin`, or None to leave the role to the next step (see [Roles](sign-in.md#roles)). Resolvers run in load order and the first answer that is not None wins. It is called only for SSO users and for Slack users without a local account, never for local accounts. A resolver that raises is asked once more when at least half of the 5 seconds are left. A resolver that still raises, answers something other than a role or None, or takes longer than 5 seconds fails closed: the page sign-in fails with no session, MCP answers 503, and Slack treats the person as not an operator, unless the person's last known role is recent enough (see [When a resolver is down](sign-in.md#roles)). The 5 seconds include the time spent waiting for a worker: all resolvers share a pool of 4 workers, and a full pool logs one warning. A hook cannot be stopped once it runs, so it must set its own timeouts on every network or database call, shorter than 5 seconds.
- **`oidc_token_request(request)`** can add to the token request of a sign-in. `request` is `{url, headers, params}` without the client secret, the code or the code verifier. It returns `{params, headers}` to add. A parameter Skopax sets itself (`grant_type`, `code`, `redirect_uri`, `client_id`, `client_secret`, `code_verifier`) and the `Authorization` header are dropped with a warning. The token request carries no `scope`, so a provider that wants one gets it here. A hook that raises stops the sign-in.

### Checks, keys and sections

- **Twin checks.** One plug-in may hold checks `c` and `c-s`, such as `tick` and `tick-cache`. Another plug-in still may not use a check id or ran key that starts with `tick-`. The instance names that twins reserve are listed under [Instances](plugins.md#instances).
- **Sub-keys.** A check may report ran keys `<k>:<x>` for any `k` in its `ran`, for example one per data source it reads. They are scoped to the instance like any ran key, and a pass clears only the cards of its own instance.
- **No data.** A pass that read nothing reports the ran key `<check>:no-data`, which clears no card at all, on any instance. A card whose own sub-key is `no-data` (a datasource or a page with that name) is therefore never cleared by a pass and closes only through the 24 h stale rule; `no-data` cannot name an instance.
- **Statuses.** An ok pass says `ok`, or `ok` and one or more of these tails after a middle dot (U+00B7), in this order: `no data` (every read part found nothing), `no data for <part>, <part>` (some did), `read <n> of <m> <things>` (a capped read; the rest stay out of `ran`), `read <n> <things>, more not read` (a capped read whose total is unknown), or `no access to <part>, <part>`. Self-review, Admin and the page count any status that starts with `ok ` as passed.
- **No access.** A read refused with HTTP 401 or 403 (or the API's own permission error) is never read as none. The refused part's cards stay open, the status names it (the tail `no access to <part>`), and the pass raises one warn card per instance and part, ranKey `<check>:access:<part>`, labelled `<Plugin> cannot read <part>: the <credential> lacks <permission>` for a 403 and `... the <credential> is invalid or lacks <permission>` for a 401, where the credential is named by its own noun (token, password, API key, keys, application, client id and secret), and `... the server requires credentials and none are set` when none is set. The pass lists `<check>:access:<part>` for every part it read or was refused, and for every part that is switched off or left out by the instance's settings, so the card closes at the first pass that reads the part again or stops reading it; a part that failed for another reason keeps its card and makes the status `error: <part>: <reason>`, while the parts that were read still count. A refused tool call returns the same sentence as the tool error. Test connection uses the permission sentence for a 403 only; a 401 there keeps the credentials text, except when the plug-in's own login or token request has just succeeded with the same credentials, where it uses the `is invalid or lacks` sentence. A log field a check needs but the index lacks works the same way: a warn card with the ranKey `<check>:fields`, listed in `ran` on every pass.
- **Once checks.** A check with `once=True` runs on the primary instance only, once per scheduled run, and its keys and cards carry no instance name. It reads the other instances through `ctx.peers` with its own plug-in id, and it waits while no primary can run. Its "What it watches" box shows on the primary only, and moving the primary keeps its cards open. When the primary moves, from Admin or from a settings source, the new primary takes over the old primary's choice of which once checks are switched off.
- **Sections.** A section name is letters, digits and dashes, starts with a lower-case letter and has at most 31 characters, so camelCase names such as `logTop` work. Core's own state names are refused. `section_help` gives a section a one-line meaning that the investigator's pass table tool shows.
- **Daily checks.** A check with `daily=True` is one whose cards may go a day or more without a pass. The check's id and every key in its `ran` join the list of daily sources, and so do their sub-keys (`<key>:<part>`) and the ran keys of its other instances (`<key>-<instance>`), so its open cards stay open for 3 days without a pass instead of 1 day, and a card that does close that way notes it was not seen. Core reads the list from the usable plug-ins at every refresh.
- **Cards off route posts.** A card with `noRoutes` true is never posted by an automatic route post, neither the first post nor the fixed message of a business route. An operator can still send it by hand from the Notify row or under More on the opened card, and the card's routes, tags and parents work as for any card. A check sets it on the card it returns, on every pass that raises the card.
- **Already active at connection.** A card a check raises may carry `startedAt`, the ISO 8601 UTC time its problem started at the source. A new card whose start is more than 1 hour (`CONNECT_GRACE_S` in `skopax.engine`) before the instance was connected is marked `alreadyActive` (`since`, `source`, the plug-in name). It opens on the board and the opened card with the line `Already active when <plug-in> was connected (since <time>)`, with the year when it is not the current one, but it is not pushed and does not count as pushed for its service, is not picked by the investigator, is not auto-assigned by a tag that a rule set (a tag a person sets still assigns it), is left out of the warning digest, and gets no Slack fallback post and no automatic route post; a person can press Investigate or Send to... as for any card. The mark stays while the card stays open. It is dropped when the card escalates, or when it reopens with a start other than the one it was marked with (a new occurrence), and both then behave as usual. A marked card that closes and comes back with the same start, for example after a maintenance window, a filter edit, a switch-off or a primary move, keeps its mark. The connection time is the earlier of the `connectedAt` of the instance record and the time core keeps in the state. Core writes `connectedAt` when an instance is created in Admin, and again when it is switched on after being off for more than 24 hours (`RECONNECT_AFTER_S` in `skopax.instances`); after a shorter switch-off the earlier time stays, so a problem that started while it was off is handled as always. A record without `connectedAt` that is switched on after a shorter gap counts as connected long ago. The time off is read from `disabledAt`, which core writes at switch-off, or else from the record's last update. The time kept in the state is set at the first pass of the check and instance that read anything: a pass that is ok and has a ran key that is not an `:access:` key, a capped read included. Core keeps that time per check and instance under `connected` in the stored state, so a restart changes nothing. Switching the instance or the check off keeps it with the time it went off: back on within 24 hours, the kept time stays, and after longer the next read starts a new one. Removing the instance drops it, and a primary move keeps it. An instance that already ran before this record existed counts as connected long ago, so its cards are never marked. Only core sets `alreadyActive`; a check that returns it has it removed. A start that is missing, unreadable or after the connection changes nothing.
- **Long checks.** A pass gets 240 seconds unless its check sets `timeout` in seconds. A check with `background=True` runs outside the shared job slots, so a long pass, such as the page scan, never holds up the other checks.
- **Run slots.** At most 4 jobs (checks and core's own jobs) run at once. When more are due, a check asked to run now goes first, then the job that has waited longest; the rest wait for the next minute. A test holds the built-in checks alone, not core's own jobs, to at most 4 that fall due in any one minute.
- **Links.** Every serving plug-in can add links to a card: the card's owner first, then the others in load order, without repeats and at most 8. Only `https://` links with a text label are kept.
- **Known cause.** A card a check raises may carry `knownCause`, a short text a person wrote in the plug-in's settings about that kind of problem, such as the Known causes field of [Batch jobs](plugins.md#batch-jobs). The opened card and the board show it as text under Known cause, and the investigator's brief gives it as a hint the team wrote that may be out of date, with `<` and `>` replaced and cut at 300 characters. Since a person wrote it, it is scanned apart from the card, like the note of a person's earlier verdict, so only the hard phrases flag in it. It is set again at every pass, so a card raised without it drops it.
- **Ids.** A plug-in setting or rule set may not take the id of a core setting. When two plug-ins share an id, the first one loaded wins, built-in plug-ins first, and the other is broken with a reason that names where the winning copy came from: built in, an installed package, or `SKOPAX_PLUGINS`. Skopax still starts: the refused copy contributes nothing, its reason is logged once as a warning at start and shows on the notices strip in Admin and on its row in Connect > Integrations, and the winning copy keeps serving the instances, rules, checks and cards saved under that id. So when a later release ships a plug-in your own package also registers, such as Dengage, the built-in one takes over on upgrade; keep the same id, field keys, check ids and card keys in both if the saved instances and open cards should carry over, then drop your copy and its entry point.
- **Own findings.** A check whose cards explain themselves, such as a send report, sets `own_findings=True`. The investigator never picks the cards whose `src` is that check's id, and neither does the Slack fallback nor the at-once post of a critical card, as for core's own page scan and Slack health cards. This holds while the plug-in is broken, locked or switched off too, so the cards its check already raised stay out of reach. Anything other than True or False breaks the plug-in.
- **Card types.** `card_types` names the plug-in's card types for the page: `CardType(sig, label, alias='')`. The board's Type filter list then shows `label` for a card whose `sig` (or, without one, `src`) is `sig`, instead of the raw id. With an `alias`, such a card is counted and filtered as that type instead, so `CardType('x-access', 'No access', alias='no-access')` puts its cards under core's No access entry. A sig and an alias are lower-case letters, digits and dashes (at most 30), a label is 1 to 40 printable characters, and a sig is not repeated; a sig that is one of the types the page already names (`CORE_SIGS` in `skopax.registry`) breaks the plug-in, while an alias may name one. The types reach the page with the plug-in list (`plugins[].types` in `GET /api/server`, and in the first render), so a type shows by its label from the first paint. Two plug-ins that name the same sig: the first one in load order wins.
- **Own auto-resolve window.** `auto_resolve` gives some of the plug-in's card kinds a window of their own: `AutoResolve(check, sig, hours, setting='')`. A card whose `sig` is `sig` and that one of the check `check`'s ran keys raised is closed as auto-resolved `hours` after it first appeared, firing or not, instead of following the general rule of core (`core.auto-resolve-hours-crit` and `core.auto-resolve-hours-warn`, counted from when a card cleared). A card someone acted on (taken, linked to a ticket, in progress, investigating, muted or already resolved) is left alone, and a resolved card that still fires stays resolved. With a `setting`, the hours come from that plug-in setting (declare it in `settings` with kind `int`, such as `Setting('auto-resolve-hours', ..., 'int', '24', 0, 720)`), so an admin can change it; a setting of 0 drops the window and the general rule applies. An entry that is not shaped as `AutoResolve` is skipped with one warning, and a setting that cannot be read falls back to `hours`. While `core.business-days` is on (the default), these hours count only Monday to Friday in the install time zone, like the general rule.

### Tools and proposals

Each `Tool` has a `kind`:

- `read`: offered in every investigator run.
- `write`: offered where core's card writes are, in card runs and in questions about cards on the page, never in Slack or chat questions or deploy reports. In shadow mode it never runs: the call is only recorded. An input that carries tool-call markup is refused.
- `propose`: offered only when someone asks in a Slack channel or thread (not in a direct message or the chat), and it changes nothing. It returns a `title` (up to 200 characters) and a `text` (up to 2000), which stay on the run once the run finishes. It also needs a `confirm` function.

A proposal is confirmed in these steps:

1. An operator chooses Confirm under the run in Activity > History (Investigator runs), or the Confirm button under the Slack answer. Two confirms at the same moment still run it once.
2. Skopax calls `confirm(ctx, args)` with a context for the instance the proposal came from and the tool's arguments. If that plug-in or instance no longer serves, nothing runs.
3. `confirm` returns a dict with a bool `ok` and a str `summary`. Anything else, or an error, counts as a failure. The summary is kept as printable text of at most 300 characters.
4. `confirm` gets 30 seconds. After that the outcome is timed out. A timed-out or failed result says the action may or may not have happened and that someone should check it, because a proposal is confirmed only once.
5. The result shows under the proposal and in the Slack thread, and goes to the activity log. On the page it is headed by its outcome: confirmed, failed, timed out, or declined when `confirm` answered with `ok` false. A result that is not ok carries its summary into the activity line, and Activity > Events marks that line.

A read tool that refuses raises `ReadError(status, message)`. The model sees the message with known secret shapes masked, cut at 300 characters by default. A refusal that needs more room, such as one that lists the allowed paths, passes it as `ReadError(status, message, room=600)`; the room is capped at 800 characters, and a room that is not a positive whole number counts as the default.

A tool may return a picture for the model: a dict with `image` (`media_type` `image/jpeg` or `image/png`, and `data` in base64), an optional `text` and optional `facts`. Core refuses a picture over 3 MB or past `screenshot.max-per-day`, stores it with the run and hands the model the picture and the text. Mark such a tool `image=True`, so the daily cap is checked before it runs.

`{field:<key>}` in a tool's description is filled, for the model, with the primary instance's value of that field. Secret fields stay empty, and the Tools page shows the field's label instead of its value. `reach` names the probe targets a tool depends on; left empty, it is every probe target of the plug-in. The Tools page marks a tool unreachable when the last probe found every one of them down, and names them in the tool's opened row.

`probe_targets(info)` gives the probe the targets of one instance: a list of dicts, each with a `name` and a `url`. Other keys are dropped, and a URL that is not `http` or `https` is reported as failed. The calls for the instances of one probe run share a deadline of 5 seconds; one that is late, raises or returns something other than a list adds no targets. The probe uses the instance's own CA certificate only when the plug-in has a field `ca` of kind `pem`, and with the instance's `ca-pinned` on accepts only the exact certificates pasted there.

`needs_field` names one of the plug-in's own fields, not a field it reads on an agent; a name that is not one of them breaks the plug-in. The tool is then offered only for the serving instances whose value for that field is set, and the Tools page shows it off ("No instance has <field> set") while none has. Confluence uses it for `spaces`. Core masks the answer of every read tool with `scan=True` before the model sees it, as it does for outside MCP servers: the instance's own secret values become `***`, then `redact.redact_secrets` masks PEM blocks, credentials in addresses, secret-looking table columns (HTML tables, and pipe tables with a delimiter row) and secret values, then what `redact` masks except card numbers (Bearer tokens, JWTs, e-mail addresses, IBANs, phone numbers that start with +, Turkish mobile numbers in the national format and Turkish national identity numbers; other long numeric IDs such as order, account or metric ids are kept as they are), and a text value under a secret-named key becomes `[redacted]`. So a committed config file read through a code tool shows `password: [redacted]`. A national identity number is masked only when its 11 digits start with 1 to 9 and pass the official checksum, and is not part of a decimal such as `12345678950,00`, so most order ids and resource versions of that length stay. A national mobile number has a 501, 505 to 509 or 53x to 56x prefix (so HTTP codes 500, 502, 503 and 504 followed by digits stay) and is written `0532 123 45 67`, `05321234567`, `0532 1234567`, `(0532) 123 45 67`, `0 (532) 123-45-67`, with `0090` or `90` before it (`90 532 123 45 67`), or, without the 0, `532 123 45 67` or `532 123 4567` with a space, dash or dot between the groups. A number that starts with 0 or a country code is also found after a colon, comma, equals sign or a number and a space (`tel:0532 123 45 67`, `10:00:00 05321234567`); one without them is kept after another number (`12 532 123 45 67`), so number columns stay. A bare `5321234567`, `532 1234567`, `0 532 1234567` and a number that runs on into a short digit group (`532 123 45 67 89`) are kept, and landline numbers are not masked. A plug-in can call `redact.redact_secrets(text)` itself for text that goes anywhere else.

`Tool(..., available=fn)` applies only together with `needs_field` and replaces that stored-value test with `fn(runtime, instance)`, for a tool that needs something other than one field set (Website offers `screenshot` when the instance has a browser, its own or a picked Headless browser instance); `needs_field` still names the field shown when the tool is off.

### Outbound

`Plugin.outbound = Outbound(post, tags_field='tags', mentions_field='mentions', link_field=None, keys_field=None, sev_field=None, target_field=None, ready=None)` makes each instance of the plug-in a route, as Teams and Email route do. The fields name the instance fields core reads: card tags, mentions (e-mail addresses) and card key patterns, each a text field, the address posts go to (any field), and the route's lowest severity (a choice within `info`, `warn`, `high` and `crit`). A plug-in whose `outbound` breaks this is not loaded.

- `link_field` names an https web link, such as a webhook; a route whose link is not one is skipped. A route that posts somewhere else names that field as `target_field` instead, a text field such as the Email route's recipients: core then needs it filled, and compares its words in lower case and in any order. A plug-in sets one of the two, never both.
- `ready(ctx)` answers None when the route can post, or a sentence saying what it needs. While it answers a sentence the route is skipped and its instance shows the sentence as an error in Connect > Integrations; The Email route uses it to say it needs the Mail server integration.

- Core picks what to post and when. `post(ctx, message)` sends one message and answers `{'ok': True}`, or `{'ok': False, 'status': <HTTP status>}`. Either answer may carry `reason`, a plain sentence that core shows for the route in place of `HTTP <status>`: on a success it says what still went wrong, such as an address that was refused. A failed answer with `'retry': False` is not tried again: core gives up on that card for the route at once. A failed answer with `'progress': True` says the post got part of the way, such as some of a list mailed: core tries it again at the next delivery and counts no try, so the plug-in must make progress on every such answer. The message holds `kind` (`action`, `info`, `fixed`, `card` or `test`), `title`, `text`, `why`, `lines`, `link`, `chat`, `page`, `board`, `mentions`, `card`, `cards`, `more`, `kids`, `teams`, `urgent` and `attribution` (the "powered by" line as `text` and `href`, or none). Each row of `cards` may carry `finding`, the investigator's summary of the card as plain text (lines separated by newlines), once the investigation has finished; a plug-in shows it under the row's `what`, labelled with `msg('routes.finding')`.
- `lines` come in the order core gives, with core's labels in the outbound language: for `action` the why first, then Recommended; for `info`, Info first, then the why. Render them in that order, so every chat tool leads with the same words.
- Core reads three plug-in settings by id when the plug-in declares them, and uses its defaults otherwise: `repeat-days` (7), `min-sev` (while it is not set, `warn` for a route with tags and `high` for a key route) and `fixed-posts` (off). See [Microsoft Teams](plugins.md#microsoft-teams).
- Tag routes of one plug-in whose address fields hold the same value share their posts: a card tagged for both is posted once. Core compares a hash of the value, never the value. A card's post history records the plug-in and the route, so two plug-ins may use the same route name.
- Core adds the instance field `slack-echo` (`default`, `on` or `off`, labels "Use the default", "On", "Off") to every plug-in that declares `outbound`, unless the plug-in declares a field of that name itself. A plug-in needs no code for it.
- `POST /api/routes/send` (operator) posts one card by hand, through one route or through every route that takes it. See [Hook time limits](#hook-time-limits) for the 10 seconds a post gets.

### Echo to Slack

Core can tell Slack where a card went, for any plug-in with an `outbound`, with no code in the plug-in. `skopax.contract.ECHO_FIELD` (`slack-echo`) and `ROUTE_ECHO` are the instance field core adds to every such plug-in, unless the plug-in declares a field of that name itself: a choice of `default`, `on` or `off`, shown as "Use the default", "On" and "Off". A route echoes when its field is `on`, or when it is empty or `default` and the core setting `routes.slack-echo` (Admin > Settings > Slack, `ROUTES_SLACK_ECHO`, default off) is on; `off` never echoes. Existing instances keep their values; an empty field means "Use the default".

The echo is a queue the route worker drains, never a call on the request or the route post:

- After a route post succeeds, in a pass or in `POST /api/routes/send`, core records the routes to name on the card (`routeEcho.pending`) and answers at once. A by-hand send calls Slack never.
- Each route-worker pass then drains the queue within a time budget, one bounded call per card, so one slow card cannot drop the next.
- A card with a Slack post gets the line in its thread. A card without one is posted to Slack in the normal way only when Slack is on, the `slack-autosend` feature is on, the card is not muted, no unsent Slack post text exists for it (on its way or kept for a person), no post claim is on it, auto-send would still treat the card as live (not handled, not a merged child, not cleared below warning) and no Slack post of it is in flight. Pods share one store: before posting, a pod takes a short claim on the card there, and the line is named in one conditional write that reports which routes it named, so two pods never post twice or say a line twice. The claim lasts about twice the route timeout, measured from the moment it is taken; a duplicate is possible only if a hung Slack post outlives the claim and the 5 minute backoff of a failed try. A post Slack accepted but core could not record counts as a failure. The backoff applies only to top-level posts and failed lines: a card that gets its Slack post by another path hears its line at the next pass. Otherwise the line waits, and the pass after Slack posts the card by any path (auto-send, an operator, a critical card) says it. A waiting line is dropped after 24 hours, with an info log. A failed Slack post or line backs the card off, 5 minutes doubling to 6 hours, is recorded in Activity, and after 5 failures the queued entries are dropped with an info log. Cards drain oldest queued line first.
- One line names every route queued for the card: `Sent to <route> on <plug-in name> (tag: <tag>)`, routes separated by `;`, no tag part for a route that took the card by key. The route is the instance name and the plug-in name is `Plugin.name`.
- A route is named once per Slack thread, and the name is recorded before the Slack call, so a timed-out call can lose a line but never repeats it. A later post to a named route adds no line; a route not named before adds a line naming only the new routes. Fixed posts are not echoed.
- The wording is the messages `routes.echo_line`, `routes.echo_item`, `routes.echo_tag`, `routes.echo_tags` and `routes.echo_for`, so a locale pack or layer can reword them. Under the line the echo quotes what the route sent, taken from the posted message and not written again: the sentence and the why of a business route, or the finding of a technical one. The text is masked once, cut at about 400 characters, and a text that several routes sent shows once; when the routes sent different texts each one is shown under its route names. Every name and every quoted text reaches Slack escaped, with its markdown characters swapped for look-alikes, so `<!channel>` and bold marks in a name stay inert, and a long line is cut without splitting an entity.
- A Slack failure is logged without the error's text and never blocks or retries the route post; a failed route post queues nothing.

### Card sentences

`Plugin.card_text(card)` writes a card's business sentence, the action a business route posts (see [Microsoft Teams](plugins.md#microsoft-teams)). Core calls it once on every pass, for every open card whose sentence no one else wrote, with a read-only copy of the card, and it answers the sentence or None. Core makes that copy once per card and pass and hands the same one to every hook: it reads like a dict (its lists are lists), `json.dumps` takes it, and any write to it or to a dict or list inside it raises `TypeError`, which counts as a failed hook for that card. `copy.copy(card)` or `copy.deepcopy(card)` gives a plain copy the hook may change. Core asks before it starts writing the pass into the state, so a slow hook never holds that write; a cleared card is not asked, and a card that another write changed in the meantime keeps its sentence until the next pass.

- The first answer in load order wins, and core stores it as `business = {text, by: 'rule', at}`, cut to 500 characters. An unchanged answer keeps its `at`.
- A sentence a person or the investigator wrote is never replaced, and the hook is not asked about that card.
- When every hook answers None, or an empty text, a sentence a hook wrote earlier is removed.
- A hook that raises, answers something other than text or None, or is late leaves that card as it was for the pass, and the hooks after it are not asked about it. The calls of one pass share 10 seconds (`HOOK_TIMEOUT_S`); once they are spent, the cards still to come keep their sentences until the next pass. A late hook is not called again while it still runs: a pass that finds the plug-in still busy with another pass waits for that call to end, within its own 10 seconds, and past them leaves its cards as they were. A call that has already run longer than the hook time limit counts as stuck, and a pass skips that plug-in at once instead of waiting. One warning per plug-in and pass names what happened: a hook that failed or was late, or (`Busy`) another pass that held the plug-in until this pass's deadline.
- Only serving plug-ins are asked. Anything other than a function or None breaks the plug-in.

`Plugin.knowledge` (a tuple of `Knowledge(id, title, text, slack=False, inline=False)`, a title of one line of at most 80 characters and a text of at most 8000) reaches the investigator in two ways. Some entries go into the prompt whole, headed `## <title> {#<id>}` and opened with `From plug-in <name>.`: in a card run the entries of the plug-ins that own the run's cards, and in every run an entry with `inline=True`, for working notes that apply to any card (the Jira and GitLab notes are inline). An inline entry may hold at most 2000 characters, or its plug-in does not load. Inline entries are shown whole, in load order, up to 6000 characters of text in all; the card owners' entries have their own budget of 16,000 characters of text and do not count against the 6000. An entry that does not fit its budget is never cut: it goes to the index whole, like any other, and stays readable through the tool. Every other entry gets one line in a plug-in knowledge index at the end of the prompt (`` - `<id>`: <title> (plug-in <name>) ``, in load order; the entries shown whole are left out of it, so the prompt grows by a line per entry and not by its text), and the core read tool `plugin_knowledge` reads one index entry in full by its id. A read is a tool call like any other and counts against the run's tool calls. Page questions with no card, chat and deploy-report assessments get the inline entries and the index. The tool is offered only in a run with at least one index entry, and its `id` lists exactly those entries; an id outside them, such as an entry of a plug-in that does not serve or whose only tools are held, is refused without its text. Slack asks and chat list and read only the entries with `slack=True`, and an org pack with `plugin_sections=False` leaves out both the inline entries and the index, so the tool is not offered.

### Org packs

An `OrgPack` lets one plug-in replace the investigator's instructions for one company:

- `process`: the process text, Markdown with `## Heading {#id}` sections; at most 200,000 characters, with at least one `{#id}` section.
- `gate` and `small_talk`: the prompts of the gate that screens Slack messages and of the small-talk reply; at most 40,000 characters each. They use only the plain fields `{product}` and `{org}` (About your company), and a literal brace is written twice.
- `slack_sections`: the ids of the sections the Slack and chat prompt keeps, taken from the pack's own process text or, without one, from core's.
- `plugin_sections=False` leaves the other plug-ins' knowledge sections, and the knowledge index, out of the prompts. The Jira working notes are one of them (how to find, read and propose tickets), and core's process text does not repeat them: with such a pack and Jira serving, the investigator knows the Jira tools by their descriptions only, unless the pack's own process text says how to use them.

The first active plug-in with a pack, in load order, wins. Another plug-in's pack is ignored, logged once and listed on the notices strip in Admin. A pack that breaks one of these rules breaks its plug-in, and core's prompts stay in use. Core's sections on untrusted input and on confidential data (`confidential-data`) are kept in every prompt, whatever the pack says: a pack's own section with either id is replaced by core's, and a pack that leaves them out still gets them.

### Locale packs

A `Locale(lang, ...)` adds a language. `lang` is a tag of two or three lower-case letters, optionally followed by a dash and a region or script of 2 to 8 letters or digits, such as `de` or `pt-BR`; a tag with two such parts, such as `zh-Hant-TW`, is not valid, and a pack with such a tag is left out whole. Skopax ships built-in packs for `tr`, `de`, `es` and `fr` under `skopax/locale/<lang>/` (`page.json`, `messages.json`, `chat.json`, `chainlit.json`, `writing.txt` and `secret-words.txt`). They are always on, pass the same checks as a plug-in's pack, and load before every plug-in pack. A plug-in pack for the same language wins text by text: a page text, message, chat text, writing note or Chainlit text it carries replaces the built-in one, its rules and tails are tried before the built-in ones, and every text it leaves out stays built-in. Message or chat texts for `en` or `en-*` are dropped, so built-in English stays as written. Every part is optional:

- `messages`: translations keyed by core message key (see `skopax/messages.py`). Only core message keys translate, so a plug-in cannot add texts of its own this way, and only the texts Skopax sends out use them. An entry whose key is not a core key, whose `{fields}` differ from the English text, that writes a field other than as a plain `{field}` (a format spec such as `{count:>9}` or a conversion such as `{product!r}`), or that holds a control character other than a newline or more than 4000 characters is dropped with one warning, counted on the notices strip like any other text, and English is sent.
- `writing`: a note to the investigator on writing in this language, at most 1000 characters.
- `page`: exact English page texts and their translations. A key may not start with `@`.
- `rules`: pairs of a regular expression and a replacement, for page texts that carry values; at most 200. A pattern has at most 300 characters, no lookbehind, and must not match the empty text. A replacement has at most 500 characters and refers to groups only as `$1` to `$9`.
- `months` and `days`: names for `Jan` to `Dec` and `Mon` to `Sun`, used in shaped texts and inside the groups a rule captures.
- `tails`: pairs of an English ending and its translation, for a known page text followed by that ending; at most 50.
- `headers`: translations used only in table headers; at most 200.
- `chainlit`: the texts of Chainlit's own buttons and labels in the chat page, as a tree that follows Chainlit's `en-US` file: names, then names, with a text at each end. Core writes the tree at boot, and again on each refresh, as Chainlit's translation for the tag (`fr.json` for `fr`) and, for a tag with no region, also under the region form browsers ask for, taken from Python's locale alias table (`fr-FR.json`, `ja-JP.json`), so Chainlit finds an exact file and logs no missing translation. Each file is the tree laid over Chainlit's own `en-US` file, so a key the tree leaves out shows in English, and it is written whole or not at all. When a locale goes away, core removes the files it wrote for it and puts back Chainlit's own file of that name, if Chainlit has one; it never touches files it did not write. A tree that cannot be written leaves out only that locale's files, with one warning, and the other locales are written. Names are letters, digits, `_` or `-`, the tree is at most 6 levels deep with at most 1000 texts, and each text is not blank, has at most 1000 characters, and obeys the link and Markdown rules of the chat texts below. A tree that breaks a rule is left out whole, with one warning, and the locale's other parts stay. A tag of `en` or `en-*` writes nothing.
- `chat`: the chat texts, keyed by the names in `skopax/chattext.py`. Each text keeps exactly the plain `{fields}` of the English text, with no format spec or conversion, is not blank and has at most 500 characters. `starters` holds 1 to 6 pairs of a button label and the message the button sends, and `actions` and `kinds` translate some of their entries.

A text that breaks one of the rules in this section is left out, with one warning in the log that names the plug-in, the language, the text or part, and the reason. Admins also see it without the log: the notices strip has one line per plug-in and language with how many texts show in English, and that plug-in's card in Connect > Integrations lists the first five of them. That text then shows from another pack or in English, and the plug-in keeps working: its checks, settings, tools and hooks are not affected. Only that one entry is left out: a page or message key, a rule, tail, header, month or day name, a chat text or entry, or a starter pair. A whole part is left out only when the part itself is not the expected list or map, or holds more than its limit, and then each text it held counts. A chat key that is not text is left out alone, and an empty `starters` list adds none, so the English starters show.

Each built-in pack folder may also hold `secret-words.txt`: words that name a secret in that language, one per line, such as `parola`, `Kennwort`, `contrasena` or `mot de passe`. Core reads the files of every language at start, whatever the outbound language, since a log line can be in any language, and adds the words to the English ones (`password`, `token`, `secret` and so on) that mark a secret value, a secret table column, a secret element and a secret-named key. A word is letters and single spaces, at most 40 characters; a space also matches `_`, `-` or nothing, so `mot de passe` covers `mot_de_passe` and `motDePasse`. Case does not matter, but list each spelling with and without accents (`sifre` and the dotted form) and each suffixed form you want (`sifresi`). A line that breaks the rule is left out with one warning. Plug-in packs do not carry secret words.

Chat texts also follow these rules:

- **No links.** The chat builds its links itself, so no chat text, starter or entry may hold a web address (`http://`, `https://`, `www.`), an e-mail address (`mailto:`, `xmpp:`, `name@host.tld`) or a `<scheme:` link, in upper or lower case, also when spelled with a backslash escape (`https\://`) or a character reference (`&#64;`).
- **Joined texts.** The chat joins some texts into one line: `halted` with `halted_stopped` or `halted_capped`, and `call` or `calls` with `last`. When a joined pair makes an address, from one pack or from the packs of two plug-ins, both texts of the pair stay English, with one warning in the log.
- **Starter messages.** A starter's message is sent as the person's own message and reaches the investigator as written. It is one line, and it may not hold Markdown or HTML marks either: `*`, `_`, a backtick, `~`, `<`, `>`, `\`, `&`, `](`, `]:` or `![`. It may not start with a space or a tab (four of them make a code block), `#`, `|`, `-`, `+` or a number followed by `.` or `)`. Its label is button text, so a mark there shows as written.
- **Shown as text.** Pack texts in chat messages and steps are escaped for Markdown and collapsed to one line, and so are the values Skopax fills into them. Button labels, starter labels and the thread name keep the text as written.
- **Placeholders.** A chat text holds the same placeholders as its English text: for example `not_ready` has `{needs}`, `feature_off` has `{feature}` and `refused_failed` has `{reason}`. A pack text whose placeholders differ does not match the English text, so it is left out with a warning that names the key, and that text shows in English.

The page loads the built-in packs first, as `/static/i18n-<lang>.js`, then one script per plug-in and language, `/plugins/<id>/i18n-<lang>.js`, and the packs of several plug-ins merge in load order. The parts other than `page` arrive under the reserved keys `@rules`, `@months`, `@days`, `@tails` and `@th`, so the script of a pack with `page` texts only is a flat map of English texts to their translations. For each text the page tries, in order: a header translation, the exact text, a known text with a tail, the text's shape (numbers as `{0}`, `{1}` and so on, month names as `{M}`, day names as `{D}`), and then the first rule that matches. A rule the browser rejects is skipped with one console warning. Because a rule is tried last, a core exact, tail or shape match beats a plug-in rule for the same text (exact, then tail, then shape, then rules).
