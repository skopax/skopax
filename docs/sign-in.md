# Sign-in

Single sign-on, roles, local accounts, the MCP server and setting all of it from the environment.

## Sign in with SSO

Skopax signs people in with any OpenID Connect provider. Set it up in Admin > Access & sign-in, on the Single sign-on card:

1. Set `SKOPAX_BASE_URL` to the public address of Skopax. It is read at boot, so a change needs a restart. The card shows the redirect URI to register, `<SKOPAX_BASE_URL>/authorized` (or `SSO_REDIRECT_URI` when that is set; its path must be `/authorized`). Register it at the identity provider for a confidential client that uses the authorization code flow.
2. Enter the issuer URL (https, or http on localhost), the client ID and the client secret. Skopax reads the rest from the provider's discovery document; "Advanced: endpoints and token request" sets the authorize, token and keys URLs and the client authentication (`auto`, `post` or `basic`) by hand, and holds Extra token request headers (see [Headless setup](#headless-setup)).
3. Choose Test connection. It checks the discovery document, the issuer it names, the S256 code challenge, the RS256 signing keys, the client authentication, the redirect URI and the scope, each with a fixed sentence. It never calls the token endpoint, so the client secret is checked at the first sign-in.
4. Choose Save. The switch is on by default, so Save turns SSO on once the settings are complete; Save & turn on shows only while the switch is off. The login page then offers "Sign in with SSO". A sign-in in the first 15 seconds after SSO comes on may need a second try.

Until an issuer, a client ID other than the default or a secret is entered, the card reads "Not set up". The Chat page needs SSO at boot: when SSO is set up in Admin after boot, Chat waits for a restart.

**Claims come from** says which token gives the email, name and roles. `id-token` (the default) reads the ID token: the scope must include `openid` (the default scope is `openid email profile`), and the token must carry this login's nonce. `access-token` reads the access token instead, for providers that put the roles only there: it must then be a JWT signed with the provider's keys, issued by the provider, for this client ID. Every sign-in uses PKCE with S256 and checks `state`; tokens are RS256 only, and their times may be 30 seconds off.

The email is the first of `email`, `preferred_username` and `sub` that looks like an email address, in lower case. An `email_verified` of false is always refused; with Require verified email on, a token without `email_verified` true is refused too. While Allowed email domains is set or New accounts is `added-only`, only the token's own `email` claim counts, and only with `email_verified` true (see [Who may sign in with SSO](#who-may-sign-in-with-sso)).

The client secret is write-only: it is sealed with `SKOPAX_SECRET_KEY` (or the generated key) and never shown, logged or written to the change history. A secret from the environment or a settings source is read-only in Admin. Changes to these settings are written to the activity log as access lines, which only admins see.

**The switch is an emergency stop.** Switching SSO off ends every SSO session on the page and refuses every MCP token issued before the stop, on every pod within 30 seconds, and they stay ended when SSO is switched on again: people sign in again. API tokens made from single sign-on sessions are refused too: every API token made from a single sign-on session that exists when SSO is switched off stays refused after it is switched back on, so make new ones afterwards; Admin > Access & sign-in tags them "Refused by the SSO stop". Password logins go on. After the stop, Slack still acts with an SSO user's stored role; to end that, disable the person in Admin. This holds wherever the switch is set (Admin, the environment or a settings source). Admin asks before switching off, and before a Reset that turns SSO off, which reads "Reset (turns SSO off)". Admin refuses to switch SSO off while no active local admin with a password exists, unless the request comes with the bootstrap token or an API token made from a password session, so that someone can still sign in; an API token made from a single sign-on session does not count, because it stops working as soon as single sign-on is off.

## The sign-in button

The login page shows the password form, an "or" divider and the SSO button, all full width. The Sign-in button group on the Single sign-on card sets how the SSO button looks, with a live preview of unsaved edits:

- **Button text** (`sso.button-text`, `SSO_BUTTON_TEXT`): at most 40 characters, such as "Sign in with Acme". Empty uses "Sign in with SSO".
- **Button icon** (`sso.button-icon`, `SSO_BUTTON_ICON`): `auto` (default), `company` or `none`.
  - `auto` picks a mark from the issuer host: `login.microsoftonline.com` and `sts.windows.net` give the Microsoft logo, used as Microsoft's sign-in branding guidelines allow: only with the text "Sign in with Microsoft" and their button colours, so with Button text set the key icon shows instead. `accounts.google.com`, `*.okta.com` and `*.oktapreview.com`, `*.auth0.com`, `*.onelogin.com`, `*.jumpcloud.com`, `gitlab.com` or a `gitlab.` host, a `zitadel.` host or `*.zitadel.cloud`, an `authentik.` host or an `/application/o/` path, and a `keycloak.` host or a `/realms/` path give a one-letter tile, not the provider's logo. Hosts match exactly or as a whole subdomain, so a look-alike such as `accounts.google.com.example.net` gets the neutral key icon, like any other issuer.
  - `company` shows an image uploaded on the card: PNG, WebP or SVG, at most 64 KiB, shown at 20 px. The type comes from the file's bytes. An SVG may hold only shapes and paint: the elements `svg`, `g`, `path`, `rect`, `circle`, `ellipse`, `line`, `polyline`, `polygon`, `defs`, `linearGradient`, `radialGradient`, `stop`, `clipPath`, `mask`, `symbol`, `use`, `title` and `desc`, in the SVG namespace; presentation and geometry attributes such as `fill`, `stroke` and the `stroke-*` ones, `d`, `x`, `y`, `width`, `height`, `viewBox`, `transform`, `points`, `offset`, `stop-color`, `opacity`, `clip-path`, `mask`, the gradient attributes, `id` and `class`; paint references only as `url(#id)`; and `href` or `xlink:href` only on `use`, pointing at `#id` with no spaces; `xml:space` may be `preserve` or `default`. Attribute values are ASCII and at most 4096 characters, an `id` is a plain name, and there are at most 32 `use` elements, none of them pointing at an element that holds a `use`. Anything else is refused, among it `style` elements and attributes, text, animation, links, images, scripts, event attributes, `foreignObject`, other namespaces, `xml:base`, processing instructions other than the XML declaration, a DOCTYPE or entity, an encoding other than UTF-8, nesting deeper than 64 or more than 64 attributes on one element. Export logos as plain SVG; editor metadata (Inkscape, Illustrator) is refused. The image is stored in the database (collection `sso_icon`, one document) and served at `GET /login/sso-icon`, open without a login, with `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox`, `X-Content-Type-Options: nosniff` and its own type; the login page links it with a version, which is cached for a year. Each pod keeps the icon state for 10 seconds, so after an upload or removal another pod can show the old icon for up to 10 seconds. A request for a version that is not the current one answers 404 without reading the database. Remove deletes it after a confirmation. Uploads and removals are written to the activity log as access lines, without the image. Admin API: `PUT /api/admin/sso/icon` with the raw image as the body and its type as `Content-Type`, `DELETE /api/admin/sso/icon`; both answer with the single sign-on view, whose `icon` says `set`, `type`, `size` and `version`.
  - `none` shows the text only.

The built-in marks are files under `skopax/web/icons/sso/`, served at `/icons/sso/<name>.svg`; THIRD_PARTY_NOTICES.md lists their sources.

Icon API (admin role for the first two): `PUT /api/admin/sso/icon` takes the raw image as the request body (PNG, WebP or SVG, at most 64 KiB; 413 when too big, 422 when the file is not an accepted image) and answers with the single sign-on settings; `DELETE /api/admin/sso/icon` removes it. `GET /login/sso-icon` serves the stored image without a session; `?v=<version>` pins the version the page was rendered with (a stale version answers 404) and makes the answer cacheable, no `v` answers with `no-cache`.

## Who may sign in with SSO

Two settings on the Single sign-on card decide who an SSO sign-in lets in. Both are checked before any account is made, changed or linked, and a refused page sign-in shows the same "The login could not be completed." as every other refusal, so the page sign-in never tells whether an account exists.

Both settings rely on the provider's verified `email` claim. While either is set, the address that is checked against the domains, matched to an account and given to a new account is the token's own `email` claim, never `preferred_username` or `sub`, and `email_verified` must be true, whatever Require verified email says. A token without both is refused before anything is written: on the page with the usual "The login could not be completed.", over MCP with "This account may not sign in".

- **Allowed email domains** (`sso.allowed-domains`): email domains such as `example.com`, separated by commas. A domain matches exactly and without regard to case: `example.com` lets in `ana@example.com` but not `ana@eu.example.com`, and there are no wildcards. Empty lets every domain in. On the card the domains are chips: Add or Enter adds the typed domain, and a domain still in the box when you choose Save is saved too. It applies to every SSO sign-in, on the page and over MCP, also to existing SSO accounts and to linking a local account. Add user refuses an SSO account (the "Signs in with SSO" switch on) and an SSO link at another domain, with a message under the email; a password-only local account may have any domain, so a break-glass admin stays possible.
- **New accounts** (`sso.new-accounts`): `anyone` (the default) gives an account to anyone the identity provider signs in; `added-only` lets in only people who already have one, added in Admin or made by an earlier sign-in. A refused new email gets no account, and the page sign-in writes one access line to the activity log. A local account with an SSO link still links under `added-only`.

**With a public provider, `anyone` means anyone.** When the issuer signs in any account at all, for example a consumer Google sign-in, `anyone` lets every such account in as the default role. Set allowed domains, or `added-only` and add people in Admin.

While the provider cannot be reached, new sign-ins fail, people already signed in stay signed in, and the notices strip says so. Removing someone at the identity provider does not disable them in Skopax: to offboard a person, disable them in Admin > Access & sign-in.

## Roles

- `viewer`: reads everything and changes nothing on the board: no card actions, no assigning, no investigator or chat questions. Viewers only manage their own account, notifications and chats.
- `operator`: everything a viewer can do, plus working cards (take, assign, resolve, mute, notes) and asking the investigator, on the page or in the chat.
- `admin`: everything an operator can do, plus users, roles, API tokens and settings in Admin.

At each SSO sign-in the role comes from the first of these that gives one:

1. a plug-in's `role_resolver` hook (see [Sign-in hooks](extending.md#sign-in-hooks));
2. the claim mapping: the values in the roles claim, looked up in the role map;
3. the role an admin set for the person in Admin;
4. the default role (`SSO_DEFAULT_ROLE`, `viewer` or `operator`).

The roles claim (default `roles`) is a claim name or a dot path; a text value is one value and a list gives its text items. The role map is a list of value and role pairs, at most 50, matched exactly; when several match, the highest role wins. Maps saved in Admin are at most 4000 characters as JSON. With no role map saved, the values of `SKOPAX_ADMIN_ROLE` (default `SKOPAX_ADMIN`) and `SKOPAX_OPERATOR_ROLE` (default `SKOPAX_OPERATOR`) map to admin and operator, and Admin shows those pairs as "in use now". Saving any role map replaces them, so add them as rows to keep them. A Keycloak realm role, for example:

    SSO_ROLES_CLAIM=realm_access.roles
    SSO_ROLE_MAP=[{"value": "ops-admins", "role": "admin"}, {"value": "ops-operators", "role": "operator"}]

In Keycloak, turn on "Add to ID token" on the realm roles mapper, since the default `id-token` mode reads the roles from the ID token.

Or a groups claim:

    SSO_ROLES_CLAIM=groups
    SSO_ROLE_MAP=[{"value": "ops-admins", "role": "admin"}, {"value": "ops-viewers", "role": "viewer"}]

A role set by the identity provider or a resolver is read-only in Admin, marked "from sign-in provider"; change it at the provider. An admin can still disable the person in Admin. A sign-in never demotes the last active admin: the role is kept, a warning is logged, and a later sign-in demotes them once another active admin exists.

In Slack, a local account acts with its stored role, and an SSO user with the resolver's answer or else the role of their last sign-in. Someone who presses a card, task or proposal button in Slack without the operator role is told so, only to them, and how to get access: with single sign-on on and no account yet, to sign in to the page once (with its address when the base URL is known), and then to ask an admin for operator access when new sign-ins get the viewer role; when only added people may sign in (`SSO_NEW_ACCOUNTS=added-only`), to ask an admin to add them; with an account that is only a viewer, to ask an admin for operator access. When roles come from a role map, a role resolver or the sign-in provider, the line only says to ask an admin for access; someone whose email domain is not allowed, or whose account is disabled, gets the refusal alone.

**When a resolver is down.** A resolver that raises is asked once more if at least half of its 5 seconds are left. If it still fails, the person may go on with their last known role: Last known role (minutes) on the Single sign-on card in Admin > Access & sign-in (`roles.stale-max-minutes`, or `SSO_ROLE_STALE_MAX_MINUTES`; 0 to 1440, default 60) is how old that role may be; the card's Save saves it with the other single sign-on edits.

- **Page and MCP.** When a resolver gave the person their stored role within that many minutes, they sign in with it, and one warning names the plug-in, the failure and how old the role is ("using the last known role from 12 min ago"). Such a sign-in does not renew the role, so the limit counts from the last answer the resolver gave. Without a role from a resolver, with an older one, or for a person signing in for the first time, the sign-in is refused (the page fails with no session, MCP answers 503).
- **Slack.** The last answer of the operator check is used while it is younger than the same limit; after that, the person is not an operator in Slack.
- **0** turns this off: a failing resolver refuses everyone, on every channel.

API tokens have their own role, never above their creator's, and stop working when their creator is disabled. A token can also get an expiry when it is made (Never, 7, 30 or 90 days, or 1 year; `POST /api/admin/tokens` takes `name`, `role` and an optional `expiresDays`, a whole number from 1 to 3650; leave it out for a token that never expires): from then on it is refused. The token list shows a warning chip from 7 days before the expiry and a red chip after it, and the API tokens tab of Admin > Access & sign-in flags API tokens while one of them does.

## Adding people

Admin > Access & sign-in has four tabs, People, Single sign-on, API tokens and MCP sign-in, and shows one at a time. Each tab counts its section and marks one that needs attention: single sign-on switched on but not set up, an unreachable provider, an expired SSO link, a token near or past its expiry, or MCP switched on while single sign-on is off. The tabs work with the arrow keys, Home and End. The open tab is in the address (`#t=access/sso`, `#t=access/tokens`, `#t=access/mcp`; People is `#t=access`), so a reload or a shared link opens the same tab, and a search hit on a sign-in or MCP setting opens the tab that holds it. Each section loads on its own and says when it did not load, with Try again. People lists each person with their role, how they sign in (Password, SSO or both) and their last sign-in; search matches name or email without regard to case or accents, and a role filter narrows the list. The role is changed with the select in the row. The row menu holds Edit name, Reset password (a dialog with the rules and what it does; Set a password for an SSO person), Turn into local account (before the first sign-in of an SSO-only account) and Disable or Enable sign-in. The last enabled admin cannot be demoted or disabled, and neither can the last enabled admin with a password while another admin signs in with SSO only: those controls are locked, with the reason as their tooltip. A password reset here, or a change in the user menu, ends that person's other password sessions within 30 seconds; the session that changed its own password stays signed in, and SSO sessions go on. There is no delete: disable a person to stop their sign-in.

**Names.** An admin renames anyone with Edit name in the row menu: a small dialog saves on Enter or Save and closes on Escape (API: `PATCH /api/admin/users/{email}` with `name`, 1 to 120 characters; the activity log gets an access line). Each signed-in person can change their own name with Edit name in the user menu (API: `PATCH /api/me` with `name`, from a page session only; API tokens cannot rename); this also adds an access line to the activity log. Saving the same name again changes nothing and logs nothing. Control characters and bidirectional override or isolate characters are removed from a name; a name left empty by that is refused. The sidebar shows the new name at once. Single sign-on fills in names too: the name is the token's `name` claim, else `given_name` and `family_name` together, else `preferred_username`, else the email. A sign-in without any name claim never replaces a name with the email, except the setup name "Admin". A sign-in on the page replaces the name only while it was never chosen: the setup name "Admin" of an account made from `SKOPAX_ADMIN_EMAIL`, the email used as a name, the part of the email an admin left as the name in Add person, or a name the provider gave before. While that holds, the name follows the provider at each sign-in. A name an admin or the person chose is kept. An account with no recorded name source follows the provider when its name is its email; otherwise an SSO account follows the provider, and a local account keeps its name unless it is "Admin". Sign-ins over MCP name only new accounts, because MCP access tokens often carry no name.

Admin > Access & sign-in > People > Add person opens a card with the email, an optional name (empty uses the part of the email before the `@`), the role and, while SSO is set up and on, a "Signs in with SSO" switch that starts on. The card checks the fields before it sends anything and shows each problem under its field.

- **Signs in with SSO, no password:** an SSO-only account. It is an SSO account added ahead of its first sign-in, with the role picked here, marked as set in Admin. It has no password, so a password login with that email fails like any wrong password. The list shows it as "SSO only" and "Not signed in yet" until the first sign-in opens it. That first sign-in, on the page or over MCP, needs no link, but it needs a token whose own `email` claim is this email and whose `email_verified` is true, whatever Require verified email says, as for a link. Once it is open, it signs in like any SSO account. An MCP sign-in stamps the last sign-in time only when none is recorded yet, so an account used only over MCP does not read "Not signed in yet"; later MCP use never moves it. An account added before this rule counts as open. Its role then follows [Roles](#roles): a resolver or a role map match still wins over the role set here, and with neither the role set here stays.
- **Signs in with SSO and a password:** a local account with an SSO link waiting 7 days for its first sign-in, as below.
- **Switch off, or SSO not on:** a local account with a password of 12-256 characters.

Until its first sign-in opens it, an SSO-only account can get a password with Turn into local account: it becomes a local account with the password and an SSO link that waits 7 days, unless the email is outside the allowed domains, which makes no link. The role and Disabled choices sent with it are saved in the same step as the password, so a refusal such as the last admin leaves the account as it was. Once it has signed in, it stays an SSO account without a password.

## Local accounts and SSO

Local accounts (from setup, `SKOPAX_ADMIN_EMAIL` or Admin) and SSO accounts are separate. An SSO sign-in whose email belongs to a local account is refused and never changes that account.

To let a local account sign in with SSO, an admin turns on its SSO link in the users list. The next SSO sign-in to that email within 7 days links it, but only with a token whose own `email` claim is that email and whose `email_verified` is true. The link pins that identity provider account (its issuer and subject): from then on only it signs in, and another account at the provider with the same email is refused. A linked account keeps its password and the role set in Admin; claims and resolvers do not change it. Turning the link off ends the account's SSO sessions within 30 seconds. A link not used within 7 days expires, and Allow again starts a new one.

Keep a break-glass local admin, with a password and no SSO link, at an address that no SSO user has, for example admin@example.com. It keeps working when the identity provider is down.

## MCP

**MCP status.** The MCP sign-in tab starts with a status block, also in the `mcp` object of `GET /api/admin/sso` (admins only). A pill reads Connected, Waiting or Not set up. Connected reads "N people in the last 7 days" with the time of the last MCP sign-in and the person's name; Waiting reads "Set up, no one has connected yet"; Not set up names the first missing piece: single sign-on not on, the MCP server switch off, or no issuer known. Below it the block lists single sign-on (on or off), the MCP endpoint (mounted or switched off) and the client ID, audience and issuer in use, each marked "default" when no value is set for it. The server keeps one small record per person in the `mcp_use` collection: the time of the last MCP sign-in, written at most once a minute per person, never a token or any secret. It covers every MCP sign-in, an SSO account and a local account with a bound SSO link alike, so people who only use MCP are counted. In Admin > Access & sign-in > People, a person with MCP use shows "MCP only" (never signed in on the page) or "Page and MCP", with the last MCP use under the last sign-in; page-only people show nothing extra. Someone who used MCP before the record existed is judged once, at their first recorded MCP use after the upgrade, from what the server already holds: an action by them from the page (not made over MCP, Slack or an API token), a page chat question, or an access or admin activity row means "Page and MCP"; only actions made over MCP mean "MCP only"; nothing at all reads "Uses MCP" until their next page sign-in, which turns it into "Page and MCP".

The MCP server (the MCP server switch, and Connect MCP on the page) needs SSO set up and on; while SSO is not active, `/mcp` answers that MCP is not set up.

Register the MCP client at the identity provider as a public client, separate from the page client: client ID `skopax-mcp` (or the MCP client ID), the authorization code flow with PKCE and no secret, a redirect to `http://localhost` on any port, access tokens whose `aud` is that client ID (or the MCP audience), and the `SKOPAX_MCP` role (or the MCP required role) in the roles claim. Keep the MCP client separate from the page client: with the same client ID, a page ID token also opens MCP. AI assistants sign in at the same identity provider: `<SKOPAX_BASE_URL>/.well-known/oauth-protected-resource` names it, and every call carries the access token as a Bearer token. The MCP settings are on the MCP sign-in card of Admin > Access & sign-in; its one Save saves every changed field, and a refused field keeps what was typed and says why.

A token is taken only when:

- it is signed with the provider's RS256 keys, and its issuer is the MCP issuer (default: the origin of the authorize URL, else the issuer URL) or the issuer the provider names;
- its audience is the MCP audience (default: the MCP client ID, `skopax-mcp`) or the MCP address itself, `<SKOPAX_BASE_URL>/mcp`;
- with MCP allowed clients set, its `azp`, `client_id` or `cid` names one of them;
- the roles claim set on the Single sign-on card holds the MCP required role (default `SKOPAX_MCP`; empty lets any token through);
- it was issued after SSO was last switched off.

Then the same rules as the page apply: the email must be there and not unverified, and a local account opens MCP only through its SSO link, with a token whose own issuer and subject match the link. A token under the MCP issuer alias is refused for a linked local account. A disabled person is refused on the next call, and on every pod within 30 seconds; a demotion takes effect within the same 30 seconds.

The role of each call follows [Roles](#roles), read from that call's token; a linked local account keeps its stored role. A viewer gets the read tools only: `list_cards`, `get_card`, `get_investigation`, `investigator_status`, `list_deploy_reports`, `list_my_asks`, `get_ask`, `list_notifications` and `about`. An operator or admin also gets `investigate_card`, `ask`, `take_card`, `resolve_card`, `mute_card`, `reopen_card`, `assign_card` and `link_ticket`. An ask over MCP runs with the role of that MCP call. API tokens and the bootstrap `SKOPAX_TOKEN` never open MCP.

The MCP handshake names the server (the display name, or Skopax) and carries the Skopax version, and the instructions open with one sentence that says who it is: "Skopax 0.5.15." for a plain install, or "Acme Ops, powered by Skopax 0.5.15, extended by acme-layer 2.3." once a display name is set and plug-ins from another package are loaded. The `about` tool gives the detail for any signed-in MCP user: the version, the edition, skopax.io and the server address, which packages extend the install and which of their plug-ins they bring, and every loaded plug-in with its version and state (ok, off, incompatible, locked or failed), capped at 40 with "and N more". Admins also see why a plug-in is not ok; viewers and operators do not. It shows no paths, settings or secrets. When the Enterprise switch hides "powered by Skopax", the sentence and `about` drop the Skopax name, version and site and keep the edition, the extending packages and the plug-ins. The sentence is read again for every new MCP session, so a changed display name or extension shows without a restart.

## Headless setup

Everything on the Single sign-on and MCP cards can also come from the environment. Each entry gives the environment name, then the setting id where Admin stores it; `SSO_REDIRECT_URI` and `SSO_TOKEN_HEADERS` are environment only. A value saved in Admin overrides the environment, and Reset goes back to it. The client secret is the exception: one from the environment or a settings source wins, and Admin shows it as read-only; one entered in Admin is stored sealed, apart from the settings.

- `SSO_ISSUER` / `sso.issuer`, `SSO_CLIENT_ID` / `sso.client-id` (default `skopax`), `SSO_CLIENT_SECRET` / `sso.client-secret` (stored sealed), `SSO_SCOPE` / `sso.scope` (default `openid email profile`).
- `SSO_ENABLED` / `sso.enabled`: default `true`. SSO is active only when it is also set up.
- `SSO_CLAIMS` / `sso.claims`: `id-token` (default) or `access-token`.
- `SSO_CLIENT_AUTH` / `sso.client-auth`: `auto` (default), `post` or `basic`.
- `SSO_REQUIRE_VERIFIED_EMAIL` / `sso.require-verified-email`: default `false`.
- `SSO_AUTHORIZE_URL` / `sso.authorize-url`, `SSO_TOKEN_URL` / `sso.token-url`, `SSO_JWKS_URL` / `sso.jwks-url`: endpoints that replace discovery.
- `SSO_REDIRECT_URI` (environment only) replaces the redirect URI made from `SKOPAX_BASE_URL`. `SSO_TOKEN_HEADERS` (environment only): extra headers for the token request, as `Name: value` pairs separated by semicolons; these values are never shown in Admin.
- `SSO_EXTRA_TOKEN_HEADERS` / `sso.extra-token-headers`: Extra token request headers, for an identity provider or API gateway that wants a header such as a channel or an API version on the token request. Write `Name: value` pairs separated by semicolons, such as `X-Channel: web; X-Api-Version: 2`; a value cannot hold a semicolon. They go on the token request only, never on discovery or the keys (JWKS) fetch, and a token request plug-in hook sees them. At most 10 headers; a name takes only the characters HTTP allows in a header name, a value takes printable Latin-1 characters only (no line break or other control character), a name may appear once, and `Authorization`, `Proxy-Authorization`, `Cookie`, `Host`, `Content-Length`, `Content-Type`, `Accept`, `Accept-Encoding`, `Transfer-Encoding`, `Connection`, `Expect`, `TE`, `Upgrade`, `Keep-Alive`, `Trailer`, `Forwarded`, `Origin` and any `X-Forwarded-*` header cannot be set. Admin refuses a wrong value with the reason, and a wrong value in the environment or the config file stops the boot. A stored value that no longer passes these rules is left out, with a warning in the log that gives the reason, never the value. A header here replaces one of the same name from `SSO_TOKEN_HEADERS`. These values are plain settings: Admin shows them and the settings history keeps them, so a secret does not belong here; keep a secret header in `SSO_TOKEN_HEADERS` or in a token request plug-in hook.
- `SSO_ROLES_CLAIM` / `sso.roles-claim`: default `roles`.
- `SSO_ROLE_MAP` / `sso.role-map`: a JSON list; unset means from `SKOPAX_ADMIN_ROLE` / `SKOPAX_OPERATOR_ROLE`.
- `SSO_DEFAULT_ROLE` / `sso.default-role`: `viewer` (default) or `operator`.
- `SSO_NEW_ACCOUNTS` / `sso.new-accounts`: `anyone` (default) or `added-only`. Another value stops the boot.
- `SSO_ALLOWED_DOMAINS` / `sso.allowed-domains`: email domains separated by commas; default empty, every domain. A value that is not a domain stops the boot.
- `SSO_BUTTON_TEXT` / `sso.button-text`: at most 40 characters; default empty, "Sign in with SSO". `SSO_BUTTON_ICON` / `sso.button-icon`: `auto` (default), `company` or `none`; see [The sign-in button](#the-sign-in-button).
- `SSO_ROLE_STALE_MAX_MINUTES` / `roles.stale-max-minutes`: 0 to 1440, default 60; see [When a resolver is down](#roles).
- `MCP_CLIENT_ID` / `mcp.client-id` (default `skopax-mcp`), `MCP_AUDIENCE` / `mcp.audience` (default empty: the MCP client ID), `MCP_ALLOWED_CLIENTS` / `mcp.allowed-clients` (default empty: any client), `MCP_REQUIRED_ROLE` / `mcp.required-role` (default `SKOPAX_MCP`), `MCP_ISSUER` / `mcp.issuer`, `MCP_SCOPE` / `mcp.scope` (default `mcp`) and `MCP_RESOURCE_URL` / `mcp.resource-url` (the public address of Skopax that MCP clients see, without `/mcp`, when it differs from the base URL).

The compose file passes none of these through; add the ones you use under the `skopax` service's `environment:` in `docker-compose.yml`.
